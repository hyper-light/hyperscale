# AD-24: Rate Limiting (Client and Server)

**Decision**: Rate-limit per client and per operation on the server (authoritative, sliding windows gated by node health) and cooperatively on the client.

*History:* this AD first specified token buckets. The server's limiter is a `SlidingWindowCounter`
(`reliability/sliding_window_counter.py:11`); the unused `TokenBucket` was deleted (REMAINING_WORK_PLAN
Phase 6, 2026-10-05).

**Rationale**:
- Prevents any single client from overwhelming the system
- Server-side is authoritative; client-side is cooperative
- A sliding window bounds every span of W seconds, so a limit can be derived from the protocol's own send rate
- Per-client tracking enables fair sharing

**Implementation**:
```
┌─────────────────────────────────────────────────────────────────┐
│                    Rate Limiting Architecture                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Client-Side (cooperative):                                     │
│  ├─ Pre-flight check before sending                            │
│  ├─ Respects server's rate limit headers                       │
│  └─ Delays requests when approaching limit                     │
│                                                                 │
│  Server-Side (authoritative):                                   │
│  ├─ Per-client, per-operation sliding windows                  │
│  ├─ Returns 429 with Retry-After when exceeded                 │
│  └─ Different limits for different operation types             │
│                                                                 │
│  Sliding Window Parameters:                                     │
│  ├─ window: RATE_LIMIT_WINDOW_SECONDS (derived if unset)       │
│  ├─ max_requests: per operation (derived or unbounded)         │
│  └─ health gate: BUSY/STRESSED/OVERLOADED tighten admission    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## As built: health-gated sliding windows

The server side is `ServerRateLimiter` over `AdaptiveRateLimiter`
(`hyperscale/distributed/reliability/`): per client (peer address) and
per operation, a `SlidingWindowCounter` of W seconds. HEALTHY and BUSY
nodes apply the per-operation limits (BUSY also refuses LOW priority);
a STRESSED node holds every client to one budget across all its
operations; an OVERLOADED node refuses everything but CRITICAL. CONTROL
traffic (AD-37) is never limited. The transport admits every TCP request
against the handler's operation (`HANDLER_RATE_LIMIT_OPERATIONS`; an
unlisted handler draws from a budget named for itself), and some handlers
also check an operation by the address their request names.

Every node (manager, gate, worker, client) builds its limits from its Env
with `AdaptiveRateLimitConfig.from_env(env, accepted_connection_cap)`.

## Limits and their derivations

Each limit is an Env setting; unset (None) it takes the derivation below
(`hyperscale/distributed/reliability/rate_limit_derivation.py`).

**Window.** `RATE_LIMIT_WINDOW_SECONDS`, derived as
`OVERLOAD_CURRENT_WINDOW x OVERLOAD_SAMPLE_INTERVAL_SECONDS` (10 x 1s =
10s): a client's rate is judged over the span the node's overload detector
averages its own load over.

**Sends per span.** A sender that sleeps at least T between sends sends at
most `floor(W / T) + 1` in any span W long (one can sit at each end).

**Estimate bound, 2.** The counter estimates a span as the current
window's count plus the previous window's count weighted by its overlap
with the span. A sender within N per span holds at most N in each window,
so the estimate is at most 2N, and reaches it when the previous window's N
sat at its start. Every derived limit is 2 x the protocol's maximum: a
legitimate sender at its maximum is never refused; one sustaining more
than twice it always is.

| Operation (handlers) | Protocol bound | Formula | Default |
|---|---|---|---|
| `heartbeat` (`manager_status_update`, `manager_resource_gossip`) | one per peer per `MANAGER_HEARTBEAT_INTERVAL`, no retry | `2 x (floor(W / MANAGER_HEARTBEAT_INTERVAL) + 1)` | 6 |
| `progress_update` (`workflow_progress`) | the flush loop sends each running workflow's latest update once per `WORKER_PROGRESS_FLUSH_INTERVAL` pass, no retry; a worker runs at most C workflows | `2 x C x (floor(W / WORKER_PROGRESS_FLUSH_INTERVAL) + 1)` | 402 x C |
| STRESSED per-client budget (all operations) | a worker's AD-37-throttled progress (one per workflow per flush + `WORKER_BACKPRESSURE_THROTTLE_DELAY_MS`) plus a manager's heartbeats | `2 x (C x (floor(W / (flush + throttle)) + 1) + floor(W / MANAGER_HEARTBEAT_INTERVAL) + 1)` | 2 x (19C + 3) |
| `stats_update` (`windowed_stats_push`), `job_submit`, `job_status`, `workflow_dispatch`, `cancel`, `reconnect`, `default` (every other handler and operation) | request-driven: volume grows with the jobs or workflows a caller runs, which no setting caps (no concurrent-jobs bound; `MAX_WORKERS_PER_MANAGER` unset by default; a workflow may finish at once, so a core's dispatch rate has no floor) | unbounded unless configured | unbounded |
| tracked clients | each connection is counted under its peer address (transport) and its named address (handlers) | `2 x accepted-connection cap` (`MERCURY_SYNC_MAX_ACCEPTED_TCP_CONNECTIONS`, else half `RLIMIT_NOFILE`); unbounded with no cap | 2 x cap |

C is `WORKER_MAX_CORES`, else the enforcing host's logical core count (an
upper bound of the physical cores a worker on that host allocates). A fleet
whose workers have more cores than the host enforcing the limit sets
`WORKER_MAX_CORES`, or the limit itself.

An operation with no protocol bound has no legitimate maximum to derive,
so a per-operation limit could only refuse legitimate work. Its floods are
shed by the health-gated states: they raise the node's load, and a
STRESSED node holds every client to the budget above; an OVERLOADED one
refuses all but CRITICAL. Operators may set any of these limits as policy.

Each idle client's counters leave after `RATE_LIMIT_CLIENT_IDLE_TIMEOUT`;
a refusal for an overloaded node asks the sender to come back after
`OVERLOAD_SAMPLE_INTERVAL_SECONDS`.

`tests/unit/distributed/reliability/test_rate_limit_derivation.py` drives
each derived limit with seeded protocol settings on a virtual clock:
legitimate senders at their maximum are never refused, floods are.
