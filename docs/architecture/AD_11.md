# AD-11: State Sync Retries with Exponential Backoff

**Decision**: State sync operations use retries with exponential backoff.

**Rationale**:
- Network partitions are often transient
- Single-attempt sync may miss temporarily unavailable workers
- Exponential backoff prevents thundering herd on recovery

**Implementation**:
- `ManagerStateSync` (`nodes/manager/sync.py`) builds one `RetryConfig` (`:91-98`):
  `max_attempts = state_sync_retries + 1`, `base_delay = state_sync_timeout_seconds / (2**retries - 1)`
  (so the backoffs together span one sync timeout), `max_delay = state_sync_timeout_seconds`, full jitter.
- `sync_state_from_workers` (`:100`, used at `:128`) and `sync_full_state_from_manager_peers` (used at `:243`)
  run each request through `RetryExecutor` with it.
- Retried: a request refused or reset in transport (a target restarting) and a not-ready answer
  (`StateSyncNotReadyError`, a target still starting). A timeout is **not** retried: it already spent a whole
  budget on an unresponsive target, and SWIM's verdict governs from there.
- After exhausting retries, the error is logged and sync continues with the other peers.
- Test: `tests/unit/distributed/manager/test_state_sync_retries.py`.
