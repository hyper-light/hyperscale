# AD-38: Global Job Ledger with Per-Node Write-Ahead Logging

**Decision**: Implement a tiered durability architecture combining per-node Write-Ahead Logs (WAL) with a globally replicated Job Ledger for cross-datacenter job coordination, with operation-specific durability levels and separate control/data planes.

**Related**: AD-20 (Cancellation), AD-33 (Federated Health Monitoring), AD-35 (Vivaldi Coordinates), AD-36 (Cross-DC Routing), AD-37 (Backpressure)

**Implementation status (2026-10-06)**: Built, on per-job Raft.
- Every manager and gate started by `hyperscale run` has a data directory, so each keeps an fsync'd `NodeWAL` under a `JobLedger` (`ledger/job_ledger.py`, `ledger/wal/node_wal.py`).
- The eight event types in Part 1 are emitted, together with `JobRelinquished`, `JobDatacenterReassigned` and `JobLeadershipAcquired`. All eleven are replayed by `ledger/job_event_applier.py:42-52`.
- A REGIONAL commit proposes one `LedgerAppendCommand` to the job's own Raft group (`raft/ledger_replicator.py`). The manager wires it at `nodes/manager/server.py:1144`, the gate at `nodes/gate/server.py:1423-1424`.
- GLOBAL means the entry's holders span two or more regions (`nodes/gate/ledger_region_span.py`; plan decision D14). A gate tier that sits in one region commits its records REGIONAL and logs that once (`_ledger_target_durability`, `nodes/gate/server.py:3503-3512`).
- Checkpoints cut the WAL (Part 7), and read consistency levels are built (Part 8, plan D2).
- The original text designed cross-region agreement as per-job VSR, Merkle anti-entropy and worker acknowledgment windows. Per-job Raft log replication replaces all three (REMAINING_WORK_PLAN header).
- The latency figures below are design targets. None has been measured (plan D16).
- Gate takeover replicas (`GateJobReplica`) are not part of this ledger. They commit by an in-memory two-phase commit across a quorum of live gates (`nodes/gate/replication_coordinator.py`, `_prepared` / `_committed_replicas`). They are neither persisted nor Raft-replicated, so they survive only while a quorum of gates stays up.

**Rationale**:
- Gates assign jobs to datacenters worldwide; job state must survive node, rack, and region failures.
- Per-node WAL provides sub-millisecond local durability for immediate crash recovery.
- Global ledger provides cross-region consistency and authoritative job state.
- Event sourcing enables audit trail, conflict detection, and temporal queries.
- Hybrid Logical Clocks provide causal ordering without requiring synchronized clocks.
- **Workers are under heavy CPU/memory load during tests and MUST NOT participate in any consensus path.**
- **Different operations have different durability requirements; one-size-fits-all is inefficient.**
- **Stats/metrics streaming requires high throughput, not strong consistency (Data Plane).**

**Operational Model**:

Hyperscale operates with three distinct node types with different responsibilities:

| Node Type | Role | Consensus Participation | Durability Responsibility |
|-----------|------|------------------------|---------------------------|
| **Gates** | Job submission, monitoring, cross-DC coordination | GLOBAL (full participant) | Job lifecycle (create/cancel/complete) |
| **Managers** | Workflow dispatch, worker health, DC coordination | REGIONAL (within DC only) | Workflow lifecycle, aggregated stats |
| **Workers** | Execute load tests (high CPU/memory) | NONE (fire-and-forget) | None - reports upward to manager |

**Critical Design Constraint**: Workers running load tests may be slow to respond (100ms+ for acks). They MUST NOT be in any consensus or acknowledgment path. Managers are the "durability boundary" within each datacenter.

## Separate Control Plane vs Data Plane

**Control Plane (Reliable, Lower Volume)**:
- Job events (create, accept, cancel, complete, fail, timeout): REGIONAL on managers. On gates they are GLOBAL when the gate tier spans two or more regions, and REGIONAL otherwise.
- Workflow dispatch: no ledger event of its own. A dispatch is refused until the job's state reaches a quorum of manager peers (`_replicate_job_state_for_dispatch`, `nodes/manager/server.py:5677`).
- Leader election: Raft (per-job groups, and the AD-52 membership group)
- Protocol: authenticated TCP frames, per-job Raft, WAL
- Requires: NodeWAL with fsync, binary format, CRC checksums

**Data Plane (High Throughput, Eventual Consistency)**:
- Progress updates from workers - LOCAL or NONE
- Stats streaming to gates - Batched, sampled
- Metrics aggregation - Eventual consistency OK
- Protocol: windowed stats, with no WAL. Workers flush their latest progress, managers collect it in time windows (`jobs/windowed_stats_collector.py`), and gates aggregate across datacenters (`nodes/gate/stats_coordinator.py`).
- Uses no ledger and no fsync

## Part 1: Event Sourcing Model

All job state changes are stored as immutable events rather than mutable state:

**Event Types**:

| Event | Fields | Semantics |
|-------|--------|-----------|
| `JobCreated` | job_id, spec, assigned_dcs, fence_token, hlc | New job submitted |
| `JobAccepted` | job_id, dc_id, worker_count, fence_token, hlc | DC accepted job |
| `JobProgressReported` | job_id, dc_id, completed, failed, hlc | Progress update |
| `JobCancellationRequested` | job_id, reason, requestor, fence_token, hlc | Cancel initiated |
| `JobCancellationAcked` | job_id, dc_id, workflows_cancelled, hlc | DC confirmed cancel |
| `JobCompleted` | job_id, final_status, aggregate_metrics, hlc | Job finished |
| `JobFailed` | job_id, error, failed_dc, hlc | Job failed |
| `JobTimedOut` | job_id, timeout_type, last_progress_hlc, hlc | Job exceeded timeout |

Three more types exist in `ledger/events/`: `JobRelinquished`, `JobDatacenterReassigned` and `JobLeadershipAcquired`. The last is journaled on manager and gate takeover.

## Part 2: Hybrid Logical Clocks (HLC)

HLC combines physical time with logical counters for causal ordering without clock synchronization:

**HLC Invariants**:
1. If event A causally precedes B, then HLC(A) < HLC(B)
2. HLC is always within bounded drift of physical time
3. Total ordering achieved via (wall_time, logical_counter, node_id)

## Part 3: Per-Node Write-Ahead Log

Each node maintains a local WAL for immediate crash recovery:

**WAL Entry Binary Format**:

```
+----------+----------+----------+----------+----------+----------+
| CRC32    | Length   | LSN      | HLC      | State    | Type     |
| (4 bytes)| (4 bytes)| (8 bytes)|(16 bytes)| (1 byte) | (1 byte) |
+----------+----------+----------+----------+----------+----------+
|                        Payload (variable)                        |
+------------------------------------------------------------------+

Total header: 34 bytes (ledger/wal/wal_entry.py)
CRC32: Covers all fields except CRC32 itself
The file opens with a format header ahead of the first frame.
```

**WAL Entry State Machine**:

```
+---------+
| PENDING | --- Written to local WAL
+----+----+
     | Regional consensus achieved
     v
+----------+
| REGIONAL | --- Replicated within datacenter
+----+-----+
     | Global ledger confirmed
     v
+--------+
| GLOBAL | --- Committed to global ledger
+----+---+
     | Applied to state machine
     v
+---------+
| APPLIED | --- State machine updated
+----+----+
     | Checkpoint created
     v
+-----------+
| COMPACTED | --- Safe to garbage collect
+-----------+
```

## Part 3.1: WAL Group Commit Architecture

NodeWAL uses one asyncio writer task (`WALWriter`, `ledger/wal/wal_writer.py`) with group commit. Hyperscale uses no threads.

**Design Principles**:
- A single writer task drains a bounded queue. File I/O goes through the Filesystem seam's executor, using F_FULLFSYNC on macOS.
- Batches writes. An idle writer sleeps until a write arrives, and the batch is whatever queued during the previous commit, up to the size limits. The original batch timeout was deleted: as an idle poll it cost about 1,500 wakeups/s per writer, measured (plan Phase 4).
- One `append_fsync` commits the entire batch
- Resolves all futures in batch after fsync completes
- A failed append is cut back to the last committed length, and its batch fails. An accepted write is never dropped.

**Throughput Model**:

| fsync Latency | Batches/sec | Entries/Batch | Entries/sec |
|---------------|-------------|---------------|-------------|
| 500μs | 2,000 | 100 | 200,000 |
| 500μs | 2,000 | 1,000 | 2,000,000 |
| 100μs (NVMe) | 10,000 | 100 | 1,000,000 |

**Write Pipeline**:

```
Writers (concurrent)        WALWriter Task              Disk
     │                           │                        │
     ├─► append(entry1) ────────►│                        │
     ├─► append(entry2) ────────►├─► write(batch)        │
     ├─► append(entry3) ────────►├─► fsync() ───────────►│
     │                           │                        │
     ◄── future1.resolve() ◄────┤                        │
     ◄── future2.resolve() ◄────┤                        │
     ◄── future3.resolve() ◄────┤                        │
```

**Batching Parameters** (`ledger/wal/wal_writer_config.py`):
- `batch_max_entries`: Max entries per batch (default: 1,000)
- `batch_max_bytes`: Max bytes per batch (default: 1MB)
- `queue_max_size`: 10,000. A full queue refuses new writes (`WALBackpressureError`).

**Recovery Path** (`NodeWAL._recover_existing_file`, `ledger/wal/node_wal.py:140`):
- Runs once at startup and reads the whole file through the Filesystem seam. Checkpoint cuts keep the file bounded.
- A torn format header is rewritten. A file in an unrecognized format is set aside, loudly, and the WAL starts empty.
- Frames are parsed up to the first torn or corrupt frame. A torn tail is cut and its bytes preserved in a sibling file (`WALTailDiscarded`); damage with written bytes after it is refused (`WALUntrustworthyError`, the node does not start). See Part 3.2.

**File Handle Safety**:
- Every append, fsync and atomic rewrite is a single Filesystem-seam call, so no handle outlives a call
- Group commits and checkpoint rewrites share the writer's file lock, so no append is lost to a rename

## Part 3.2: WAL Recovery and Damage

At open, `NodeWAL` (`ledger/wal/node_wal.py`) reads its file and parses
frames up to the first one that is torn or fails its CRC. What follows
depends on whether a power loss can explain the damage. This is the same
rule `RaftStoreCodec.replay` applies to the Raft store:

- **Torn tail: cut it.** The damaged frame is last: nothing but zeros
  (or the end of the file) follows its claimed extent, and no whole frame
  (a possible length and a CRC that holds) begins anywhere from the
  damage on. A power loss during an append that was never acknowledged
  leaves exactly this, because its batch never finished its fsync. The
  cut happens only after a second read returns the same bytes
  (`require_stable_read`). The cut bytes are preserved as
  `<wal>.discarded-<n>`, and `WALTailDiscarded` is logged.
- **Anything else: refuse to start.** This covers a damaged frame with
  written bytes or a whole frame after it, a frame whose damaged length
  claims the rest of the file while whole frames follow, a frame whose
  CRC holds but that does not decode, and a zero hole over a frame's
  length with written bytes after it (its extent is unknown, so it is
  never guessed). After a stable second read, `WALUntrustworthy`
  (CRITICAL) is logged and `WALUntrustworthyError` is raised. That error
  propagates out of `NodeWAL.open`, `JobLedger.open` and node start, and
  the file is left byte for byte as found. A flaky read path raises
  `UnstableStorageReadError` instead, and nothing is cut or condemned.

**Decision: refuse, not set aside.** The Raft store sets an untrustworthy
disk aside because Raft re-replicates everything to a new member. The job
ledger has no such path:

- The only peer catch-up is `adopt_replicated_history`, which runs when
  this node takes over a job's leadership. Nothing rebuilds a node's own
  ledger from peers.
- LOCAL-durability entries (progress, Part 3.4) are never replicated, so
  no peer holds them.

A node that set its WAL aside would therefore start without acknowledged
entries that exist nowhere else, which is the silent loss this rule
exists to prevent. Refusing matches SCENARIOS section 10 ("WAL
corruption. Detected at startup; node refuses to come up."). To recover,
the operator restores the WAL from a backup, or moves it aside to start
without the node's local history. Replicated job state comes back
through takeover adoption.

Damage confined to the last frame cannot be told apart from a torn
append, so it is treated as a torn tail. This is the residual risk the
rule accepts, and every log with this frame layout shares it.

Tests: `tests/unit/distributed/ledger/wal/test_node_wal_damage_vopr.py`
(seeded torn tails, truncation, mid-file damage, flaky reads) and
`test_node_wal_tail_recovery.py`.

## Part 3.3: Logger Suitability Analysis

**Suitability Matrix**:

| Requirement | Logger Has? | WAL Needs? | Data Plane Needs? |
|-------------|-------------|------------|-------------------|
| Async file I/O | Yes | Yes | Yes |
| Per-file locking | Yes | Yes | Optional |
| fsync guarantee | Opt-in (FSYNC / FSYNC_BATCH modes) | **Critical** | Not needed |
| Sequence numbers | No | **Critical** | Not needed |
| Binary format with CRC | No (JSON) | **Critical** | Not needed |
| Read-back capability | No (write-only) | **Critical** | Not needed |

**Verdict**:
- **Control Plane WAL**: Build dedicated NodeWAL class (built)
- **Data Plane Stats**: the windowed-stats pipeline, not the Logger (see Control Plane vs Data Plane)

## Part 4: Commit Pipeline

Three-stage commit with progressive durability guarantees:

**Durability Levels**:

| Level | Latency | Survives | Use Case |
|-------|---------|----------|----------|
| LOCAL | <1ms | Process crash | High-throughput updates |
| REGIONAL | 2-10ms | Node failure | Normal job operations |
| GLOBAL | 50-300ms | Region failure | Critical operations (cancel) |

Each level is satisfied by a replicator passed to `JobLedger`. REGIONAL is a commit in the job's Raft group, and GLOBAL is holders in two or more regions (D14). A 3-of-5-region quorum would be unreachable for most deployments. A level the node cannot meet raises `UnsatisfiableDurabilityError`, so it is never reported as met. The latencies are unmeasured targets (D16).

## Part 5: Global Job Ledger

Cross-region consensus for authoritative job state:

**Job ID Format** (encodes home region):

```
Format: {region_code}-{timestamp_ms}-{gate_id}-{sequence}
Example: use1-1704931200000-gate42-00001

Benefits:
- Lexicographically sortable by time
- Instant routing to authoritative region
- No coordination needed for ID generation
- Region encoded for fast authority lookup
```

IDs are generated by `JobIdGenerator` (`ledger/job_id.py`).

**Conflict Resolution** (superseded 2026-10). The original design merged divergent regional copies with the rules below. Every job's events are now ordered by one Raft log, so there is nothing to merge. Replay refuses events for a job that is already terminal (`JobEventApplier`), and fence tokens still order leadership. The original rules were:

1. Cancellation always wins (fail-safe)
2. Higher fence token wins (later operation)
3. HLC ordering (causal precedence)
4. Lexicographic node_id (deterministic tie-breaker)

## Part 6: Anti-Entropy and Repair

Superseded (2026-10). The design called for Merkle-tree verification and repair across regions. Raft log catch-up does that job: a lagging or new member of a job's group receives the missing entries, or a snapshot, from the group's leader (REMAINING_WORK_PLAN header). No Merkle code exists.

---

## Part 7: Checkpoint and Compaction

Efficient recovery through periodic snapshots (built: `JobLedger.maybe_checkpoint`, `ledger/job_ledger.py:1179`, run by the manager and gate tick loops):
- Checkpoint captures local state machine snapshot
- Records LSN watermarks (local, regional, global) (`ledger/checkpoint/checkpoint_model.py`)
- Enables WAL compaction. Each checkpoint atomically cuts the log to what the oldest kept checkpoint still needs (`NodeWAL.discard_through` → `WALWriter.rewrite`). Checkpoint names carry their LSN.
- State transfer to new nodes goes through Raft snapshots (AD-52), not ledger checkpoints

## Part 8: Session Consistency Guarantees

Built (plan D2). `JobStatusQuery` carries a `ReadConsistency` level (`models/read_consistency.py`). EVENTUAL reads, and reads of a terminal status, are answered locally. The job's leader answers the other levels. For STRONG, a manager first re-syncs to a quorum, and a gate re-commits its replica to a quorum. A manager follower answers SESSION and BOUNDED_STALENESS when its synced view is new enough, and otherwise forwards the read once. The CLI exposes this as `hyperscale job status --consistency/--max-staleness`.

| Level | Guarantee | Latency | Use Case |
|-------|-----------|---------|----------|
| EVENTUAL | May read stale | Fastest | Dashboards, monitoring |
| SESSION | Read-your-writes | Low | Normal operations |
| BOUNDED_STALENESS | Max lag = X ms | Medium | Cross-region queries |
| STRONG | Authoritative | Highest | Status verification |
