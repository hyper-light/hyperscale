# AD-53: AD-30 Cross-Layer Death Escalation

## Status

Proposed (2026-05-14).

## Context

AD-30 introduces a two-layer hierarchical failure detector: a global layer
that tracks machine-level liveness (driven by SWIM probes / Lifeguard
suspicion) and a job layer that tracks per-(job_id, node) responsiveness
based on recent progress signals. The two layers were designed to be
independent so that either one can drive a death decision and the other
can either corroborate or refute. AD-30's "Reconciliation Loop" section
explicitly lists "Detect inconsistencies between layers" as a
responsibility of the coordinator.

In the manager implementation as merged, only the global layer can
declare a worker dead. The job-layer scaffolding exists —
`ManagerHealthMonitor.suspect_job`, `check_job_suspicion_expiry`,
`_on_worker_dead_for_job`, the `_worker_job_last_progress` timestamps
maintained by `record_job_progress` — but the wiring is incomplete:

* `suspect_job` has **no caller** in the manager. Job-suspicions are
  never created from stale progress; the dictionary stays empty.
* `_on_worker_dead_for_job` only schedules per-job sub-workflow
  reassignment. It does **not** feed back into the global incarnation
  tracker, so the worker remains `ALIVE` from SWIM's perspective until
  the probe walk reaches it.

The consequence is that dead-node reap latency for a worker in active
workflows is bounded by the SWIM probe walk:

```
T_reap ≈ probe_index(worker) × protocol_period + suspicion_timeout
```

At single-prober, protocol_period ≈ 1 s, suspicion ≈ 5–8 s, and bulk
failures of N workers serialize against the probe walk. The Phase 3
`test_mass_crash_50_workers` and `test_graceful_scale_down_50_workers`
budgets (120 s and 90 s respectively) absorb this for small N, but at
N = 50 the walk plus indirect-probe + suspicion stretches past budget
without parallelism — and bare probe parallelism (raw `K` probers per
period) is a load-profile change AD-30 deliberately did not adopt
(see "Trade-offs" in AD-30 for why composing independent signals is
preferred over multiplying probe traffic).

## Decision

The job-layer signal is wired in as a second-class confirmation source
for global death, with two new behaviors:

1. **Job-suspicion creation from stale progress** (closes the missing
   AD-30 wiring). `ManagerServer._job_responsiveness_loop` now scans for
   `(job_id, worker_id)` pairs whose last progress is older than
   `JOB_RESPONSIVENESS_THRESHOLD` (60 s default) and promotes them into
   a `JobSuspicion` with a *tight* timer drawn from
   `HierarchicalConfig.job_min_timeout` (2 s by default). The threshold
   gates **start of suspicion** ("we already waited a full
   responsiveness window for any signal"); the tight timer gates
   **declaration of job death** ("further silence past the
   confirmation window is strong evidence"). Conflating the two — the
   pre-extension code defaulted both to the same env value — meant
   that even after wiring `suspect_job`, total time to job-death would
   be 2 × threshold. Separating them preserves the long
   "give-the-worker-a-chance" budget for false-positive resistance
   without paying for it twice.

2. **Cross-layer escalation to global DEAD**. When
   `check_job_suspicion_expiry` returns a `(job_id, worker_id)`,
   `_escalate_job_death_to_global(worker_id)` runs in addition to the
   existing per-job reassignment path. It looks up the worker's UDP
   address, reads the current incarnation from
   `IncarnationTracker`, calls
   `update_node_state(addr, DEAD, incarnation, now)`, and on success
   calls `notify_node_dead(addr, incarnation, "ad30_job_layer_escalation")`
   — the exact same code path a SWIM probe-driven death takes. The
   existing `_on_node_dead_callbacks` chain (registry unregister,
   worker_pool deregister, sub-workflow reassignment, gossip update)
   runs identically.

The escalation is gated by two refutation signals so it cannot
contradict a globally-healthy worker:

* **Recent probe success** — `PeerProbeReliabilityTracker.had_recent_success(addr, within=2·protocol_period)`.
  A new predicate (alongside the existing window-smoothed
  `get_reliability`) that answers "has there been *concrete evidence*
  of SWIM-reachability for this peer recently?". Unlike
  `get_reliability` — which uses a "healthy by default" prior and
  returns `1.0` for unknown peers — this predicate returns `False`
  on no-evidence, which is the correct semantics for an escalation
  gate. Sized against the configured `SWIM_UDP_POLL_INTERVAL` so the
  gate scales with operator tuning.

* **Already-terminal in the incarnation tracker** (no state, or
  `status == DEAD`): no work to do, idempotent.

## Mapping to AD-30 design intent

| AD-30 design point | Pre-AD-53 state | Post-AD-53 state |
|--------------------|-----------------|------------------|
| Two independent layers can drive death | Only global layer drives death | Either layer can drive global DEAD |
| Job layer "triggers: job-specific communication timeout" | Trigger source unwired | Stale progress (`_worker_job_last_progress`) drives `suspect_job` |
| Reconciliation loop "detects inconsistencies between layers" | Only resolves global→job (clear job suspicions) | Now also resolves job→global (escalate to DEAD) when no contradicting probe |
| Lifeguard formula (`log(C+1)/log(N+1)`) | Lone observer means C=1, near-max timeout | Job-layer expiry plays the role of a second confirmation source for the same node, but composed at the suspicion layer rather than the bracket layer (because the job layer's evidence is *terminal*, not partial) |
| Confirmations from gossip vs. local layers | Conflated as "from_node" | Local layers feed local confirmations; gossip continues to feed peer confirmations |

The architectural pattern is the same one AD-30 cites for global death
clearing all job suspicions, in the other direction: a layer reaching a
terminal state acts on the other layer's state when there is no
refutation.

## Why not raw probe-fanout

Raw probe parallelism (`K` cooperating probers per protocol period)
also fixes the N=50 reap budget — but:

* The 4× steady-state probe traffic at default `K=4` is a load-profile
  change AD-30 considered ("Alternatives Considered: Confirmation
  Debouncing, Batch Confirmation Processing") and chose not to take.
* Fanout works because more probes catch death faster, not because
  more independent signals are being composed. AD-30's stated
  preference is signal composition. The job layer already exists, and
  its signal is independent of SWIM probing (different transport,
  different trigger).
* Fanout helps even when the cluster is healthy (wastes probes); the
  job-layer escalation only activates when there is concrete evidence
  of workflow-side silence past a long threshold.

## Why the two timing constants are independent

A single conflated timer

```
T_jobdeath = T_threshold  (60 s)
```

would have been the simplest wiring, but at burst-failure scale would
have produced

```
T_jobdeath = T_threshold + T_jobdeath = 120 s
```

(once for the wait before `suspect_job` fires, once for the suspicion
to expire) — putting us right back at the budget edge that motivated
this AD. The split

```
T_jobdeath = T_threshold + T_min_timeout  (60 s + 2 s = 62 s)
```

reflects the actual evidence flow: the long threshold protects against
ordinary worker slowness ("don't suspect until you've waited a full
worker-LHM-stretched workflow tick"); the short timer reflects the
strength of the evidence at that point ("if you're *still* silent after
we've already waited a threshold, that's terminal"). Both timers remain
operator-configurable.

## Refutation and recovery

A worker that resumes sending progress after the threshold has elapsed
but before `suspect_job` runs in the next loop iteration is naturally
refuted: `record_job_progress` updates the timestamp, the next pass of
`find_silent_worker_jobs` excludes it, no suspicion is created.

A worker that resumes progress after `suspect_job` has run but before
the tight timer expires can be refuted by `refute_job_suspicion` (the
existing AD-30 path). Today nothing in the manager calls that with the
required incarnation — a follow-up AD or implementation tightening
should wire `record_job_progress` to also refute any live suspicion
for the pair. This AD limits itself to the escalation path; refutation
wiring is non-blocking because the global-layer probe success gate
(`peer_reliability >= 0.5`) already covers the case where the worker
is still SWIM-responsive.

A worker that has been escalated to DEAD globally but is in fact alive
follows the standard SWIM rejoin path (incarnation increment via
JOIN), unchanged by this AD.

## Burst-failure speculative SUSPECT (the second signal)

The job-layer escalation above closes the AD-30 wiring for workers
running active workflows. It does **not** help workers that are alive
but idle at the workflow layer — `_worker_job_last_progress` has no
entry for them, so `find_silent_worker_jobs` cannot report them. In a
mass-crash scenario where most of the fleet is idle (e.g.
`test_mass_crash_50_workers` uses `vus=1`, so 49 of 50 workers have
nothing to report), those idle workers remain bottlenecked on the
serial SWIM probe walk.

The burst-failure signal addresses this case by composing a new
derived input into the same AD-30 global layer:

1. The prober tracks **direct + indirect probe failures** (the same
   condition that already triggers `start_suspicion` for the current
   target) in a sliding window of
   `BURST_FAILURE_WINDOW_SECONDS` (default 10 s).
2. When the observation count crosses `BURST_FAILURE_THRESHOLD` (default
   3) without an intervening successful probe, the cluster is in a
   bulk-failure regime — there is no plausible workload that produces
   three full direct+indirect failures in ten seconds against
   different targets without a real cluster-wide event.
3. `_speculatively_suspect_all_silent(self_addr)` iterates the probe
   scheduler's membership and starts global SUSPECT for every member
   that has **no recent successful probe** (via
   `PeerProbeReliabilityTracker.had_recent_success`, sized against
   `2 × SWIM_UDP_POLL_INTERVAL`).
4. Each suspicion is recorded in the timing wheel and ticks down
   concurrently per Lifeguard. Workers actually dead expire to DEAD
   at the wheel; workers that are alive but speculatively suspected
   refute via the standard incarnation-bump path (SWIM canonical).

### Why this is AD-30 signal composition, not SWIM-fanout in disguise

* The probe **traffic** is unchanged. We do not send extra probes.
  Existing probe outcomes feed an additional, derived "cluster is
  degraded" signal. AD-30's global layer is designed for exactly this
  shape of input: a callback-driven detector that takes evidence
  from any source and runs the Lifeguard timer.
* The signal is **conditional**: it activates only when there is
  concrete evidence of cluster-wide failure (`K` consecutive failures
  within `W`). In healthy operation, the observation window stays
  short and the speculative scan never fires — there is no
  steady-state cost.
* The signal is **bounded**: the window window-eviction logic gives
  the deque a hard memory bound, and the speculative scan iterates
  the probe-scheduler members exactly once per burst-entry (the
  `_burst_failure_active` flag is a one-shot per burst).
* The signal is **refutable**: a single subsequent successful probe
  clears the observation window and exits burst mode, so the
  detector cannot be permanently jammed by a transient outage.

### Why we skip `broadcast_suspicion` here

The probe-driven `start_suspicion` path is followed by
`broadcast_suspicion(target, incarnation)` so peers can corroborate
or refute. In the bulk-failure regime by definition the rest of the
membership is silent — broadcasting `K × N` UDP messages to silent
destinations is wasteful and would not affect outcomes (no peer
arrives to confirm, no peer arrives to refute except the speculatively-
suspected peer itself, and that path is via incarnation gossip not
the suspect message). The local timing wheel does the work.

### Interaction with graceful_scale_down

50 workers calling `graceful_stop` send LEAVE messages that drive
`update_node_state(DEAD)` directly — the fast path. Probes to those
workers fail after the LEAVE, which feeds the burst-failure counter.
The `had_recent_success` gate ensures the surviving worker (which is
still being probed successfully) is **not** speculatively suspected;
only the already-departed workers are caught by the speculative scan,
which is harmless because they are already DEAD in the tracker (and
`start_suspicion` short-circuits via `_is_target_already_suspect_or_dead`).

## Tests

Covered by existing Phase 3 simulation scenarios:

* `test_mass_crash_50_workers` — 50 workers killed concurrently; the
  manager's probe walk alone cannot reap within the 120 s budget, so a
  pass is direct evidence the cross-layer escalation is firing.
* `test_graceful_scale_down_50_workers_reassigns_orphans` — 50 workers
  call `graceful_stop`; the LEAVE fast path handles the bulk of
  reaping, but any worker whose LEAVE is lost (UDP burst, event-loop
  saturation) is now caught by the job-layer escalation rather than
  serializing against the probe walk.
* `test_slow_worker_churn_one_worker_every_10_seconds` — confirms the
  escalation does not false-positive a single recovering worker
  (peer-reliability gate).

## Alternatives Considered

1. **SWIM probe fanout** (`SWIM_PROBE_FANOUT > 1`) — rejected for the
   AD-30 load-composition reasons above; in-tree comment in the
   resulting commit describes the prototype that was backed out.
2. **Lifeguard `confirmation_count`-on-indirect-probe-failure** —
   conflates the SWIM peer-confirmer semantics ("a different node has
   independently confirmed") with the prober's own observations.
   Rejected.
3. **Shorten `SWIM_SUSPICION_MAX_TIMEOUT`** — reduces wait per dead
   node but doesn't help the serial walk, which dominates at high N.
4. **Move escalation to the JobSuspicionManager itself** (have the
   timing-wheel directly call `update_node_state`) — couples
   subsystems that are otherwise cleanly separated. Keeping the
   escalation in the manager's responsiveness loop preserves the
   "callbacks compose" pattern AD-30 uses for the global layer
   (`_on_node_dead_callbacks`).
