# AD-41: Resource Guards - CPU/Memory Monitoring and Enforcement

## Part 1: Problem Statement and Requirements

### The Resource Exhaustion Problem

In a distributed performance testing framework, workflows executing on workers can consume unbounded resources:

1. **Runaway workflows** - Bugs causing infinite loops or memory leaks
2. **Misconfigured jobs** - Users requesting more resources than allocated
3. **Cascading failures** - One overloaded worker destabilizing the cluster
4. **Invisible degradation** - No visibility into actual vs expected resource usage

Without resource guards, a single misbehaving workflow can:
- Exhaust worker memory, causing OOM kills
- Saturate worker CPU, starving other workflows
- Propagate back-pressure through the entire system
- Provide no signal to operators until catastrophic failure

### Requirements

1. **Accurate Monitoring**: CPU/memory usage tracked across entire process trees (workflows may spawn subprocesses)
2. **Low Overhead**: Monitoring must not significantly impact workflow performance
3. **Asyncio Compatible**: All monitoring must be non-blocking and work with asyncio event loops
4. **Hierarchical Aggregation**: Workers -> Managers -> Gates, with accurate cluster-wide totals
5. **Multi-Node Topology**: Handle multiple managers per datacenter, multiple gates per datacenter
6. **Noise Reduction**: Filter measurement noise without hiding real violations
7. **Uncertainty Quantification**: Know confidence in measurements for smarter decisions
8. **Graduated Enforcement**: WARN -> THROTTLE -> KILL progression with grace periods
9. **Pure Python**: pip-installable, no custom C code or eBPF

## Part 2: Kalman Filtering for Resource Metrics

### Why Kalman Filtering Instead of EWMA?

Resource metrics from `psutil` are inherently noisy due to:
- Context switches during sampling
- Kernel scheduling jitter
- GC pauses in monitored processes
- Subprocess spawn/exit timing

EWMA (Exponentially Weighted Moving Average) has limitations:
1. Fixed gain - cannot adapt to changing noise conditions
2. No uncertainty estimate - just a point value
3. Lag vs noise tradeoff - low alpha = smooth but laggy
4. Cannot model dynamics - assumes random walk

**Kalman Filter Advantages**:
1. Adaptive gain - automatically balances responsiveness vs smoothing
2. Uncertainty estimate - know confidence in each measurement
3. Optimal filtering - minimizes mean squared error
4. Can extend to model dynamics (acceleration, trends)

### Implementation

The `ScalarKalmanFilter` and `AdaptiveKalmanFilter` classes provide:
- Process noise (Q): variance in true value change
- Measurement noise (R): variance in psutil readings
- Automatic noise adaptation based on innovation sequence

## Part 3: Process Tree Resource Monitoring

### Design Rationale

Workflows may spawn subprocesses (e.g., browser automation, external tools). We must monitor the entire process tree, not just the root process.

**Key Implementation**:
- Uses `psutil.Process.children(recursive=True)` to traverse entire tree
- Aggregates CPU/memory across all descendants
- Handles subprocess spawn/exit dynamically
- Uses `asyncio.to_thread` for non-blocking psutil calls

### ResourceMetrics

The `ResourceMetrics` dataclass captures:
- `cpu_percent` and `cpu_uncertainty`
- `memory_bytes` and `memory_uncertainty`
- `memory_percent`
- `file_descriptor_count`
- `timestamp_monotonic` and `sample_count`
- `process_count` (live processes in tree)

## Part 4: Hierarchical Aggregation Architecture

### Multi-Node Topology

Each datacenter has multiple managers and multiple gates:

```
GATE CLUSTER (3 gates)
    │
    ├── no gate resource gossip (each gate hears every manager)
    │
    └── ManagerResourceReport (in each manager's TCP status)
            │
MANAGER CLUSTER (4 managers)
    │
    ├── gossip between managers (LocalView sharing)
    │
    └── WorkerResourceReport (in heartbeat)
            │
WORKERS (N per manager)
    │
    └── Per-workflow Kalman-filtered metrics
```

### Manager Resource Gossip

Every manager maintains:
1. **LocalView** (computed locally): self metrics + worker aggregate
2. **Peer Views** (received via gossip): other managers' LocalViews
3. **ClusterView** (aggregated): all managers + all workers

The original sketch gossiped every 2-5 seconds with 2-3 random peer views. As built, a manager sends each peer its whole state once per heartbeat (below).

### As built (2026-10)

A client can run jobs on one datacenter's managers with no gate in the path,
so the manager tier holds the same datacenter view a gate does:

1. **LocalView** is the manager's `ManagerResourceReport`: the workload of the
   workflows it *leads* (Kalman estimates from `LedWorkflowResources`) plus the
   datacenter's worker capacity (100 per allotted core of every worker that
   counts toward capacity; each worker host's memory once). Workers register
   with every manager, so leadership -- not worker ownership -- partitions the
   workload, and reports sum without double counting.
2. **Peer views** arrive by `ManagerResourceGossip`: once per manager heartbeat
   interval (`MANAGER_HEARTBEAT_INTERVAL`, the cadence the same report reaches
   gates at) every manager sends each active peer every fresh report it holds,
   each tagged with how long ago its manager made it
   (`ManagerResourceGossipMessage`, TCP `manager_resource_gossip`, telemetry
   class). A datacenter's managers are few, so whole-state messages stay small
   and converge in one round, and a manager still learns a peer it cannot
   reach directly. Ages replace the vector clock: the freshest copy of a
   report wins, and a forwarded copy ages from when its manager made it, so a
   dead manager's report expires (`RESOURCE_VIEW_STALENESS_SECONDS`) wherever
   it was passed.
3. **ClusterView** is `DatacenterResourceAggregator.view()` over every fresh
   report -- the same aggregation a gate runs on the reports in its managers'
   TCP status updates: workload summed, capacity from the newest report,
   pressures as the workload's share of capacity.

Clients read it from `ManagerPingResponse.resources` (gateless) or
`GatePingResponse` -> `DatacenterInfo.resources` (through a gate).

4. **Gates** need no resource gossip of their own: every manager sends its
   TCP status report, resource report included, to every healthy gate
   (`_gate_heartbeat_loop`), so each gate aggregates every datacenter's
   reports itself. The `GateResourceGossipMessage` of architecture.md's
   sketch would carry nothing a gate lacks.
5. **Routing** weighs a datacenter's resource pressure through its AD-42
   routing factor (AD-36 Part 4, the predictor of AD-42 Part 9) instead of
   skipping it past a fixed `cpu_pressure > 0.95`: pressure near the limit
   already ranks it after every less pressed datacenter, and a fixed cutoff
   would refuse it a job it could still take -- the only one, perhaps.
6. **Kill** goes through the workflow cancel path the manager already has
   (cancellation, its acknowledgements and retries), not separate
   `ResourceKillRequest`/`ResourceKillResponse` messages.

## Part 5: Graduated Enforcement

Built: `ResourceEnforcer` (`resources/resource_enforcer.py`). The manager constructs it (`nodes/manager/server.py:708-720`) and judges it on every progress report. The worker receives throttles in `WorkflowThrottleHandler` (`nodes/worker/handlers/tcp_throttle.py`). Test: `tests/unit/distributed/resources/test_resource_enforcer.py`, and E2E `tests/integration/cli/test_cli_resource_guard.py`.

### Enforcement Levels

| Level | Trigger | Action |
|-------|---------|--------|
| WARN | 80% of budget (`RESOURCE_GUARD_WARNING_THRESHOLD`) for the warning grace | Log warning, once per violation |
| THROTTLE | 85% of budget, once warned, for a warning grace | `WorkflowThrottleRequest` scales the workflow's concurrency by limit / estimate. Released when the workflow drops back under the warning threshold on every resource |
| KILL | estimate minus 2σ above 100% of budget, once warned, for the kill grace | Cancels the workflow through the manager's normal cancel path |
| EVICT | still violating a kill grace after the kill request is retried once (`MAX_KILL_ATTEMPTS = 2`) | Evicts the worker that ignores it |

Only CPU and memory are enforced (`ResourceViolationType`). File descriptors are sampled but have no budget.

### Grace Periods

- `RESOURCE_GUARD_WARNING_GRACE_SECONDS` (10 s) and `RESOURCE_GUARD_KILL_GRACE_SECONDS` (2 s)
- Prevents killing workflows on transient spikes
- Uncertainty-aware: each grace stretches by `1 + sigma / value`, so a noisy estimate is watched longer

```python
RESOURCE_GUARD_KILL_THRESHOLD: float = 1.0
RESOURCE_GUARD_WARNING_GRACE_SECONDS: float = 10.0
RESOURCE_GUARD_KILL_GRACE_SECONDS: float = 2.0
RESOURCE_VIEW_STALENESS_SECONDS: float = 30.0
```

A job's own budget rides `JobSubmission.resource_budget`.
