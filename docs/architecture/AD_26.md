# AD-26: Adaptive Healthcheck Extensions

**Decision**: Allow healthcheck deadline extensions with logarithmic grant reduction.

**Rationale**:
- Long-running operations may legitimately need more time
- Unlimited extensions enable abuse
- Logarithmic reduction discourages repeated requests
- Extensions require active negotiation (not automatic)

**Extension Protocol**:
```
┌─────────────────────────────────────────────────────────────────┐
│              Adaptive Healthcheck Extensions                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Base deadline: 30 seconds                                      │
│                                                                 │
│  Extension grants (logarithmic reduction):                      │
│  ├─ 1st extension: +30s (100% of base)                         │
│  ├─ 2nd extension: +15s (50% of base)                          │
│  ├─ 3rd extension: +7.5s (25% of base)                         │
│  ├─ 4th extension: +3.75s (12.5% of base)                      │
│  └─ ...converges to minimum (1s)                               │
│                                                                 │
│  Formula: grant = max(min_grant, base / (2^extension_count))   │
│                                                                 │
│  Extension request must include:                                │
│  ├─ reason: "long_workflow" | "gc_pause" | "resource_contention"│
│  ├─ estimated_completion: timestamp                            │
│  └─ current_progress: 0.0-1.0                                  │
│                                                                 │
│  Extension denied if:                                           │
│  ├─ No progress since last extension                           │
│  ├─ Total extensions exceed max (e.g., 5)                      │
│  └─ Node is already marked suspect                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Implementation**:
```python
@dataclass
class ExtensionTracker:
    """Tracks healthcheck extensions for a worker."""
    worker_id: str
    base_deadline: float = 30.0
    min_grant: float = 1.0
    max_extensions: int = 5

    extension_count: int = 0
    last_progress: float = 0.0
    total_extended: float = 0.0

    def request_extension(
        self,
        reason: str,
        current_progress: float,
    ) -> tuple[bool, float]:
        """
        Request deadline extension.
        Returns (granted, extension_seconds).
        """
        # Deny if too many extensions
        if self.extension_count >= self.max_extensions:
            return False, 0.0

        # Deny if no progress
        if current_progress <= self.last_progress and self.extension_count > 0:
            return False, 0.0

        # Calculate grant with logarithmic reduction
        grant = max(
            self.min_grant,
            self.base_deadline / (2 ** self.extension_count)
        )

        self.extension_count += 1
        self.last_progress = current_progress
        self.total_extended += grant

        return True, grant

    def reset(self) -> None:
        """Reset tracker when worker completes operation or recovers."""
        self.extension_count = 0
        self.last_progress = 0.0
        self.total_extended = 0.0
```

**Message Types**:
```python
@dataclass
class HealthcheckExtensionRequest:
    """Worker requests more time before being marked unhealthy."""
    worker_id: str
    reason: str  # "long_workflow" | "gc_pause" | "resource_contention"
    current_progress: float  # 0.0 to 1.0
    estimated_completion: float  # Unix timestamp
    active_workflow_count: int

@dataclass
class HealthcheckExtensionResponse:
    """Manager response to extension request."""
    granted: bool
    extension_seconds: float  # 0.0 if not granted
    new_deadline: float  # Unix timestamp of new deadline
    remaining_extensions: int  # How many more can be requested
    denial_reason: str | None = None  # If not granted
```

**Manager-Side Integration**:
```python
class WorkerHealthManager:
    """Manages worker health with extension support."""

    def __init__(self):
        self._extension_trackers: dict[str, ExtensionTracker] = {}
        self._worker_deadlines: dict[str, float] = {}

    def handle_extension_request(
        self,
        request: HealthcheckExtensionRequest,
    ) -> HealthcheckExtensionResponse:
        """Process extension request from worker."""
        tracker = self._extension_trackers.setdefault(
            request.worker_id,
            ExtensionTracker(worker_id=request.worker_id)
        )

        granted, extension_seconds = tracker.request_extension(
            reason=request.reason,
            current_progress=request.current_progress,
        )

        if granted:
            current_deadline = self._worker_deadlines.get(
                request.worker_id,
                time.monotonic() + 30.0
            )
            new_deadline = current_deadline + extension_seconds
            self._worker_deadlines[request.worker_id] = new_deadline

            return HealthcheckExtensionResponse(
                granted=True,
                extension_seconds=extension_seconds,
                new_deadline=new_deadline,
                remaining_extensions=tracker.max_extensions - tracker.extension_count,
            )
        else:
            denial_reason = self._get_denial_reason(tracker, request)
            return HealthcheckExtensionResponse(
                granted=False,
                extension_seconds=0.0,
                new_deadline=self._worker_deadlines.get(request.worker_id, 0.0),
                remaining_extensions=max(0, tracker.max_extensions - tracker.extension_count),
                denial_reason=denial_reason,
            )

    def _get_denial_reason(
        self,
        tracker: ExtensionTracker,
        request: HealthcheckExtensionRequest,
    ) -> str:
        if tracker.extension_count >= tracker.max_extensions:
            return f"Maximum extensions ({tracker.max_extensions}) exceeded"
        if request.current_progress <= tracker.last_progress:
            return f"No progress since last extension (was {tracker.last_progress}, now {request.current_progress})"
        return "Extension denied"

    def on_worker_healthy(self, worker_id: str) -> None:
        """Reset extension tracker when worker completes successfully."""
        if worker_id in self._extension_trackers:
            self._extension_trackers[worker_id].reset()
```

**Grant Reduction Table**:
| Extension # | Formula | Grant (base=30s) | Cumulative |
|-------------|---------|------------------|------------|
| 1 | 30 / 2^0 | 30.0s | 30.0s |
| 2 | 30 / 2^1 | 15.0s | 45.0s |
| 3 | 30 / 2^2 | 7.5s | 52.5s |
| 4 | 30 / 2^3 | 3.75s | 56.25s |
| 5 | 30 / 2^4 | 1.875s -> 1.0s (min) | 57.25s |
| 6+ | - | denied | - |

**Key Properties**:
- **Converging**: Total extension converges (geometric series)
- **Progress-gated**: Must show forward progress to get more time
- **Bounded**: Hard limit on extension count prevents indefinite delays
- **Self-limiting**: Diminishing returns discourage dependency on extensions

## Phase H Evolution (Addendum)

The Phase H series of work elevated AD-26 from a single-witness
progress-gated extension protocol to a fully cluster-aware,
adaptive, statistically rigorous extension framework. This
addendum captures the on-disk reality.

### H1: Grant-formula off-by-one correction

Original formula `grant = max(min_grant, base / (2 ** extension_count))`
applied the logarithmic reduction one cycle ahead of intent. The
first request now returns `base_deadline` verbatim (30s for the
default config), and the doubling clock advances after the
commit. Verified end-to-end against the published grant-reduction
table.

### H2: Default-deadline rule with explicit override hierarchy

Worker timeouts now resolve via a 3-tier hierarchy in
`hyperscale.distributed.health.deadline_resolver.resolve_worker_deadline_seconds`:

1. `submission.timeout_seconds_explicit` — verbatim user override
2. `workflow.timeout != base default` — `workflow.duration + workflow.timeout`
3. else — `workflow.duration × HYPERSCALE_DEFAULT_WORKER_TIMEOUT_MULTIPLIER` (default 1.5)

The multiplier is environment-configurable
(`HYPERSCALE_DEFAULT_WORKER_TIMEOUT_MULTIPLIER`).

### H3: Multi-dimensional progress witnessing

`WorkflowProgressSnapshot` (`hyperscale.distributed.health.workflow_progress_snapshot`)
replaces the single `current_progress` float with three integer
counters (`cores_completed`, `step_transitions`, `actions_completed`)
plus a monotonic `snapshot_time`. The strict-monotonic-progress
criterion is `all_non_regressed AND any_advanced`, which is
universal across workflow shapes (load tests, ETL/batch,
single-action probes) and tamper-resistant by construction —
gaming the check requires advancing every counter
simultaneously.

### H4: Worker autonomous extension trigger

`hyperscale.distributed.nodes.worker.extension_trigger.ExtensionTrigger`
polls every active workflow and fires an extension request when
`elapsed > deadline × HYPERSCALE_EXTENSION_LOOKAHEAD_FRACTION`
(default 0.75) AND any progress dimension has advanced since the
last fire. Per-workflow trackers, TaskRunner-managed loop, no
orphan tasks. This makes workers self-reporting per the user's
"workers should report. Period. Uniformity is key" directive.

### H5: Multi-witness manager-side decision

`hyperscale.distributed.health.extension_decision.ExtensionDecisionEvaluator`
orchestrates five witnesses in a pure-function `decide()`:

1. **Counter monotonicity** — H3 progress snapshot check
2. **Throughput regime** — H6 BOCPD detector (see below)
3. **Overload state** — AD-19 `health_overload_state` gate
4. **Rate limit** — `min_between_extensions_seconds` clamp
5. **Max extensions** — AD-26 hard cap

Each decision carries an `ExtensionWitnessEvidence` forensic
record consumed by H7 ledger replication and H8 outcome feedback.
Tracker mutations are committed via `commit_grant`/`commit_deny`
after the caller has ack'd the decision — `decide()` itself is a
side-effect-free value-returning function.

Structured `ExtensionDenialCode` enum (NONE, MAX_EXHAUSTED,
COUNTER_REGRESSION, NO_ADVANCEMENT, THROUGHPUT_REGIME_DOWN,
OVERLOADED_STATE, RATE_LIMITED) replaces the legacy free-form
`denial_reason` string. The wire-level
`HealthcheckExtensionResponse` carries both for backwards
compatibility.

### H6: Bayesian Online Change-Point Detector throughput witness

`hyperscale.distributed.health.progress_witness.ThroughputWitness`
wraps a Normal-inverse-Gamma conjugate-prior BOCPD detector
(Adams-MacKay 2007) with a Student-t predictive distribution. The
manager feeds it each workflow's own action rate from its progress
reports (see "Feed" below); at each extension decision it emits verdicts:

- `COLD_START` — insufficient samples
- `STATIONARY` — no change-point
- `REGIME_CHANGE_DOWN` — sustained throughput drop, deny
- `REGIME_CHANGE_UP` — recovery, treat as healthy

Hierarchical α-budget allocation (`HierarchicalAlphaConfig` with
Benjamini-Hochberg FDR splitting system→DC→manager→worker→workflow)
keeps the false-positive rate bounded across the cluster
hierarchy. Critical fix: **MAP run-length is the primary
change-detection signal**; instantaneous `cp_prob` saturates at
the hazard rate when both old- and new-run predictives are
extreme, so the run-length integral is the robust signal.

**Where α enters the decision: K-S confirmation.** A fresh MAP run
length only *proposes* a change point. The witness then splits the
stream's history at it (run-length index `r` covers the newest `r + 1`
samples) and runs the two-sample Kolmogorov-Smirnov test, pre-change
against post-change, at the per-test level `alpha_workflow`. Rejected
stationarity → `REGIME_CHANGE_DOWN` / `REGIME_CHANGE_UP` by the sign of
the predictive-mean shift; otherwise `STATIONARY`. So `alpha_workflow`
is the per-test false-deny rate the budget allocates, and
`HYPERSCALE_EXTENSION_FPR_BUDGET` bounds something real. The K-S
p-value is the asymptotic Kolmogorov one with Stephens' correction
(Numerical Recipes 3rd ed. §14.3.3), "already quite good for
N_e ≥ 4" with `N_e = n_pre·n_post/(n_pre+n_post)`; below that the
change point stays unconfirmed. The split is chosen from the same
data, so the nominal p-value is optimistic; the confirmation can only
remove BOCPD denials, never add them.

Before 2026-10-06 the K-S test instead "narrowed the baseline" at the
fixed `alpha_system`: it trimmed a history that only the K-S test
itself read, so it changed no decision, and `alpha_workflow` was
reported but gated nothing. That path and its `ks_alpha_override`
knob are gone.

**Feed: the workflow's own rate, from the progress path.** The manager's
`workflow_progress` handler passes every report of an in-flight
sub-workflow (`JobManager.sub_workflow_in_flight`: its job not ended, no
final result yet, so no stream is reopened after the workflow's end) to
`WorkerHealthManager.ingest_workflow_progress` →
`ThroughputWitness.ingest_progress`. The sample is the rate over the span
since the last sample, `Δcompleted_count / Δelapsed_seconds` on the
worker's clock. The report's `rate_per_second` is not used: it is the run's
cumulative mean (`completed_count / elapsed_seconds`), which turns a step
collapse into a slow hyperbolic decay and whose values are far from the
independent samples the K-S test assumes. The extension decision only
reads the stream (`assess`). Before 2026-10-06 the witness sampled the
worker's completions/sec once per extension decision (≤ ~6 samples per
stream, too few for any α ≤ 0.05 rank test to reject).

The sampling rate and window are derived
(`progress_witness/witness_feed_derivation.py`):

- `n` = the smallest post-change segment whose complete separation is
  significant at the α floor (1e-5), with `N_e = n(1 − 1/4) ≥ 4` (a fresh
  run is at most 1/4 of the window): **8**.
- Interval = one trigger poll (`HYPERSCALE_EXTENSION_TRIGGER_INTERVAL`,
  5 s) / 8 = **0.625 s** (the worker reports every 50 ms).
- `run_length_max` = one base deadline (30 s) as the fresh-run window:
  30 / 0.625 / 0.25 = **192**.

Cost (microbenchmark, CPython 3.14): one BOCPD update is ~208 µs at 192
run lengths (929 µs at the old 1000), so ~0.33 ms per in-flight workflow
per second (0.033% of the loop per workflow; 100 in flight → 3.3%). Taking
every 50 ms report at the old cap would have been 18.5 ms per
workflow-second, saturating the loop at ~54 workflows. The per-manager
in-flight count is bounded only by `MAX_WORKERS_PER_MANAGER` (unset by
default) × worker cores.

The run-length cap now **lumps** every run at or past the cap into its
last state (mass summed, predictive from the newest `run_length_max`
samples). The detector used to drop those runs. That discarded the regime
a stationary stream is in once the stream outlived the cap, and it read
2.4–12.5% of later samples as fresh change points. Freshness is now judged
against `min(samples seen, run_length_max)`.

Proof: `tests/unit/distributed/health/test_throughput_witness_feed.py`
(production config, Poisson workers reporting every 50 ms):
- A collapse is denied within two trigger polls at the controlled α (40
  seeds).
- Healthy throughput is falsely denied at most at the binomial bound for
  that α: 4 of 7,483 decisions over 400 seeds, 5.3e-4 against α = 5e-3.
- Removing the feed fails the test.

### H7: ExtensionLedger + AD-48 dissemination

#### H7a: Manager-side authoritative ledger

`hyperscale.distributed.health.extension_ledger.ExtensionLedger`
keeps a bounded rolling history (cap = `max_extensions × 2`) of
every decision per workflow. Three indices for O(1) lookup:

- `by_workflow_id` — primary keying
- `by_worker_id` — cascade cleanup on worker reaping
- `by_job_id` — cascade cleanup on job termination

`ExtensionDecisionEvent` is the wire-level frozen-dataclass
record; `record()` is idempotent on (fence_token, timestamp,
decision) and stale-leader-term-rejecting.

#### H7b: SWIM piggyback dissemination

A new `b"#|x"` channel runs alongside the AD-48 worker-state
`#|w` channel. `ExtensionDecisionGossipBuffer` mirrors
`WorkerStateGossipBuffer` exactly — λ × log(n+1) broadcast
budget per AD-48, idempotent on `event_id =
workflow_id|fence_token|timestamp`, higher-`leader_term` events
supersede. The wire format is 29 colon-delimited fields with
`denial_message` as the trailing variable-content slot.

`ManagerServer` overrides
`_get_extension_decision_piggyback` /
`_process_extension_decision_piggyback` to encode/decode the
channel; inbound events feed into
`WorkerHealthManager.ingest_remote_decision_event` (which is
idempotent through the ledger) and are re-added to the local
buffer so this manager continues their dissemination — that's
how the cluster fan-out reaches λ × log(n+1) hops.

### H8: Outcome feedback loop

#### H8a: Outcome event + Beta-conjugate alpha tuner

`hyperscale.distributed.health.extension_outcome.ExtensionOutcomeEvent`
captures workflow termination with `ExtensionOutcomeKind`
(COMPLETED / TIMED_OUT / FAILED / EVICTED / UNKNOWN). The Beta-
conjugate posterior in
`hyperscale.distributed.health.alpha_posterior.HierarchicalAlphaTuner`
is keyed on `workflow_class` (the workflow's Python class name)
so cross-instance learning accumulates across every load-test
run of the same class.

Posterior update: COMPLETED outcomes add +1 to α; negative
outcomes (TIMED_OUT/FAILED/EVICTED) add `1 + (1 - progress)` to
β so workflows that died early are stronger negative evidence
than ones that nearly finished.

**Composition with H6 (live).** For every throughput-witness test the
H5 evaluator calls
`HierarchicalAlphaTuner.alpha_budget(workflow_class, alpha_H6, floor, ceiling)`
(`health/extension_decision_evaluator.py`), where `alpha_H6` is the
hierarchical α from the active-workflow counts, and passes the result
to `ThroughputWitness.observe` as the K-S level. The manager resolves
`workflow_class` from the job (`_lookup_workflow_context`).

The budget is weighted multiple testing (Genovese, Roeder & Wasserman
2006, *Biometrika* 93:509): test *i* at `α·w_i`, weights averaging 1,
keeps the family budget, and power grows by giving more α where the
alternative is a priori likelier. The alternative is "this workflow is
stuck", so

```
q_pool  = (B + 1/2) / (A + B + 1)                  # Jeffreys Beta(1/2, 1/2)
q_class = (b + 1·q_pool) / (a + b + 1)             # unit-information prior (Kass & Wasserman 1995)
alpha   = clamp(alpha_H6 · q_class / q_pool, floor, ceiling)
```

with `a`, `b` the class's success and failure evidence (α, β net of the
stored prior) and `A`, `B` their sums over every held class (kept as two
running sums, so the read is O(1)). Averaged over outcomes the weights
are 1 up to the priors' pseudo-counts: the H6 budget is redistributed
between classes, not inflated. A class with no outcomes keeps `alpha_H6`
exactly. A class that times out gets more α (a throughput drop is denied
on less evidence); one that completes gets less.

The doc's earlier formula, `clamp(E[p], floor, ceiling)` with `E[p]` the
*success* mean, was rejected: it maps a success probability onto a
significance level, sends every class with `E[p] > ceiling` to the
ceiling, and gives the most α to the classes that fail least.

The stored prior Beta(0.5, 9.5) is kept unchanged because persisted
snapshots fold it into α and β; the budget reads only the evidence net
of it. `posterior_mean` stays an observability value.

**One observation per workflow.** A workflow's outcome reaches every
manager many times (λ·log(n+1) re-broadcasts per manager; the leader
hears its own echo). `WorkerHealthManager` admits each `workflow_id`
once through `AppliedOutcomeWindow`, held for the tuner's
`stale_after_seconds`; repeats leave the tuner untouched, and the
manager re-arms `#|o` dissemination only for a first copy. In-flight
outcomes emitted at job termination are keyed by the full sub-workflow
token, the id the workflow was dispatched, extended and ledgered under.

Self-cleaning: at `max_classes` (default 10k), the
least-recently-updated posterior past the staleness window
(`stale_after_seconds`, default 1 day) is evicted, after the new
outcome is applied (evicting first dropped a new class as the stalest,
since its `last_outcome_at` still read 0). Snapshots write floats as
`repr`, so a new leader restores each posterior exactly.

#### H8b: AD-48 #|o dissemination

A new `b"#|o"` channel runs alongside `#|x`. Wire format is 13
colon-delimited fields with `workflow_class` as the trailing
free-form slot. Dedup key is `workflow_id` alone (a workflow
terminates exactly once). `ManagerServer` overrides for the
piggyback hooks; followers ingest via
`WorkerHealthManager.ingest_remote_outcome_event` which is
idempotent through the ledger's stale-term rejection.

#### H8c: Leader-transfer persistence

`TimeoutTrackingState` (AD-34) gains three persistence fields:

- `last_extension_decisions: dict[workflow_id, ExtensionDecisionEvent]`
- `pending_extension_outcomes: dict[workflow_id, ExtensionOutcomeEvent]`
- `alpha_tuner_snapshot: dict[workflow_class, bytes]`

`WorkerHealthManager.persist_decision_to_tracking` /
`persist_outcome_to_tracking` mirror local state into the
tracking state; `replay_persisted_state` rebuilds local state on
takeover. The replay order is: restore tuner snapshot (the
authoritative posterior at the previous leader's last
persistence point), then replay decisions and outcomes into the
ledger ONLY — applying them to the tuner again would
double-count Bernoulli observations.
