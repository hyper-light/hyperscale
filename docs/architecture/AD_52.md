# AD-52: Cluster Creation

## Status

Proposed (2026-05-12).

## Context

Hyperscale is a long-running control plane and job server, not a short-lived test runner. Gate clusters and per-DC manager clusters are expected to run for months or years, hosting the global job ledger (AD-38), idempotency state (AD-40), SLO digests (AD-42), retry budgets (AD-44), and learned route state (AD-45). Worker fleets are ephemeral; the control plane is not.

The cluster registry and join mechanism must:

1. Work in every reasonable deployment substrate — Kubernetes, bare VMs, Mesos, Nomad, ECS/Fargate, Cloud Run, Docker Swarm, bare metal, and dev laptops — with **one** protocol path, not per-environment branches.
2. Require zero persistent storage on any node (no PVCs, no local-disk dependencies for correctness).
3. Be internal to Hyperscale; no reliance on etcd, ZooKeeper, Consul, cloud provider APIs, K8s API server, multicast, broadcast, or NTP.
4. Match the correctness bar of state-of-the-art consensus databases (etcd, CockroachDB, Spanner) and the robustness bar of battle-tested service registries (Istio, Linkerd).

Complexity is not a goal but is not a constraint either; correctness, robustness, and performance dominate.

## Decision

A unified cluster formation and membership protocol with the following properties:

- **Deterministic bootstrap** via an explicit `--initial-members` list on the founding nodes; bootstrap and join are distinct protocols.
- **Raft-replicated membership** in each cluster's existing Raft group (gate cluster, per-DC manager cluster), with **joint consensus** (C_old,new) for atomic membership changes.
- **Learner state** for new joiners: non-voting catch-up via snapshot + log streaming, promoted to voter only when log lag is within threshold.
- **Membership-generation fencing** on every cluster RPC: `(cluster_uuid, membership_epoch, sender_node_id, sender_term)` validated by receivers.
- **Pluggable seed locators** (`tcp://`, `dns://`, `dns-srv://`, `file://`, `exec://`) so any environment can produce a seed list without Hyperscale depending on environment-specific APIs.
- **SWIM + phi-accrual hybrid** failure detection: SWIM gossip drives cluster-wide convergence (AD-27, AD-30); phi-accrual drives per-edge circuit-breaking decisions (extending AD-18).
- **Watch streams** for membership distribution: leader pushes deltas, like etcd watch / xDS, with reconnect-and-resync.
- **Disconnected mode** for the data plane: every node maintains a soft-state cache of the last-known cluster view; data plane keeps serving when control plane is unreachable.
- **Cluster UUID as generation marker**, minted at bootstrap and stored in Raft state (independent of mTLS cert lifecycle).
- **Ephemeral node identity**: `node_id = uuid4()` per process start; restarts are new joins, never rejoins.
- **Determinism boundary** at the state machine apply layer: log entries are the only input to state transitions.

## Non-goals

- Total catastrophic recovery (every region's gate cluster dying simultaneously). Unrecoverable without external durability; documented as such.
- Surviving total cluster-wide configuration loss without operator intervention. Bootstrap is operator-driven.
- Automatic horizontal scaling of the control plane (gates/managers). HPA-style scaling is for workers; control plane resize is operator-triggered via explicit `ResizeCluster` log entry.
- Multicast / broadcast discovery. Unsupported in most cloud environments.

## 1. The universal environment contract

The deployment substrate must provide exactly three things. Anything beyond this is a shortcut and is explicitly rejected.

1. **A way to launch a process with config** (env vars and/or flags). Every orchestrator supports this.
2. **TCP connectivity between nodes that can reach each other** at some address. No assumption about IPv4 vs IPv6, NAT, link-local, dual-stack, or specific port ranges.
3. **A way to provide each node with a seed locator string at launch.** This is the irreducible bootstrap input.

### Explicitly forbidden assumptions

The protocol must not depend on, and must continue to operate correctly without, any of:

- Stable IP addresses across process restart.
- Stable hostnames. Hostnames are opaque label hints, never identity.
- Persistent storage of any kind. No PVCs, no local files surviving restart.
- Synchronized wall clocks (NTP not required). Ordering uses Hybrid Logical Clocks (AD-38). Wall clock is used only for observability, never for correctness.
- DNS being available, fast, or honest. If DNS fails, alternative locator types must work.
- Predictable orchestrator restart semantics. Hyperscale exits non-zero on unrecoverable error; whoever launched it decides what to do.
- Specific port numbers. Every address includes its port.
- Orchestrator-specific service discovery (K8s API, Mesos master, Consul, etc.). Hyperscale only resolves what the operator passes in `--seeds`.
- Cert lifecycle automation. mTLS material is read from configured paths; rotation policy is outside scope.
- `node_id` continuity across process restart. A restarted process is a new member, period.
- `cluster_size` knowability at join time. Founding members must agree on it at bootstrap; subsequent joiners learn it from Raft state.

## 2. Seed locator: the only environment-facing primitive

A seed locator is a URI-style string Hyperscale resolves internally. Five scheme handlers, all implemented inside Hyperscale:

| Scheme | Form | Resolution |
|---|---|---|
| `tcp://` | `tcp://10.0.5.7:8080` | Literal address. Port required. |
| `dns://` | `dns://manager.svc.cluster.local:8080` | OS-level name resolution (uses `/etc/hosts`, DNS, mDNS, NSS, whatever the OS provides). All A/AAAA records returned. |
| `dns-srv://` | `dns-srv://_hyperscale._tcp.svc` | DNS SRV record lookup. Service+port from the record. |
| `file://` | `file:///etc/hyperscale/seeds` | Read newline-delimited locators from a file. Watched via mtime, re-read on change. |
| `exec://` | `exec:///opt/get-seeds.sh` | Execute a command, parse stdout (one locator per line). Refreshed on a configurable interval (default 60s). |

`--seeds` accepts a comma-separated list of locators. Resolution semantics:

- Resolve all locators, dedupe address results.
- Re-resolve on a jittered interval (default 60s, jitter 0–20% per AD-21).
- Re-resolve on any connection failure to a previously resolved address.
- An empty resolution is not an error; the locator may produce results later.
- A locator returning 1000+ addresses is bounded by `--max-seed-candidates` (default 64); excess is sampled with weighted rendezvous hashing per AD-28.

### Environment mapping

| Environment | `--seeds` value |
|---|---|
| Kubernetes (headless Service) | `dns://manager-headless.ns.svc.cluster.local:8080` |
| Kubernetes (SRV-configured) | `dns-srv://_hyperscale._tcp.manager-headless.ns.svc` |
| Cloud VMs with cloud DNS | `dns-srv://_hyperscale._tcp.internal` |
| Cloud VMs raw | `tcp://10.0.1.5:8080,tcp://10.0.1.6:8080,tcp://10.0.1.7:8080` |
| Mesos with Mesos-DNS | `dns://hyperscale.marathon.mesos:8080` |
| Nomad | `dns://hyperscale.service.consul:8080` or `exec:///opt/nomad-seeds.sh` |
| ECS / Fargate (Cloud Map) | `dns://hyperscale.local:8080` |
| Docker Swarm | `dns://tasks.hyperscale:8080` |
| Bare metal | `file:///etc/hyperscale/seeds` |
| Dev laptop | `tcp://127.0.0.1:8081,tcp://127.0.0.1:8082,tcp://127.0.0.1:8083` |
| Air-gapped / edge | `file:///etc/hyperscale/seeds` |
| Spot/preemptible | identical to the steady-state environment |

Hyperscale's code paths are identical across all of these. Only the locator string differs.

### Security note on `exec://` and `file://`

Both schemes accept input from outside the process. The configuration paths are operator-controlled (env vars, flags); they must not be sourced from network input. The runtime enforces:

- `exec://` paths must be absolute and on a filesystem owned by the process user, with no world-writable parent directories. Otherwise it's a refused locator with a loud log line.
- `file://` paths are read with the same ownership/permission checks.
- Locator strings are never logged with full path; only the scheme is logged at INFO, full path at TRACE.

## 3. Cluster identity

Every node carries five identity fields at startup. These are the irreducible configuration.

| Field | Source | Purpose |
|---|---|---|
| `cluster_id` | `--cluster-id` | Human-readable identifier (e.g., `prod-uswest-managers`). Admission check at handshake. |
| `role` | `--role` | One of `gate`, `manager`, `worker`. Enforced against mTLS cert subject. |
| `mTLS material` | configured paths | Cert chain + key, validated against a cluster CA. Cert subject must declare the matching role per AD-28 connection matrix. |
| `node_id` | generated | `uuid4()` at process start. Never persisted, never reused, never inferred. |
| `advertised_address` | `--advertised-address` (optional) | Address peers should use to reach this node. If unset, derived from the source IP of the first successful peer handshake. |

`cluster_uuid` is **not** node configuration. It is minted at bootstrap, committed as the first Raft entry, immutable thereafter, and learned by joiners from the leader during handshake. It is the cluster-generation marker (Section 6).

### Why `node_id` is ephemeral

Three reasons:

1. **No assumed substrate has stable identity that survives all restart conditions.** K8s pod hostnames are unstable on Deployment-style workloads; cloud VM hostnames can be changed by image regeneration; bare-metal machines can be reimaged.
2. **Stable identity is an optimization, not a correctness requirement.** A restarted process being a "new member" costs two Raft log entries (REMOVE old, ADD new). This is negligible at control-plane restart rates.
3. **Simplifying the model eliminates an entire class of bugs.** No "rejoin" path means no node-identity hijacking, no incarnation-number races, no two-pods-claiming-the-same-identity edge cases.

The cost is faster eviction-then-readmission on pod restart; Raft handles this trivially.

## 4. Bootstrap protocol (cold formation)

Bootstrap is a separate operation from join. A node bootstraps only when:

- It is launched with `--initial-members=<list>` and the list includes its own `node_id`, AND
- It can successfully reach a quorum of the other initial members and confirm they are also bootstrapping the same cluster.

Otherwise, the node joins an existing cluster via Section 5.

### Why `--initial-members` is required

In my earlier drafts of this design I proposed "lowest node_id over a discovery window runs pre-vote." That approach has the following race: if seed resolution returns different views to different candidates during the bootstrap window (DNS propagation lag, partial visibility, etc.), two candidates can independently conclude they are the bootstrap leader and propose competing initial membership logs. While Raft pre-vote (AD-5) would eventually reject one, the race window admits operator confusion and observable cluster-split symptoms.

The state-of-the-art (etcd `--initial-cluster`, ZooKeeper `myid`) makes bootstrap deterministic by requiring operators to enumerate the founding members. Hyperscale follows this pattern.

### `--initial-members` format

```
--initial-members=node_id_1@locator_1,node_id_2@locator_2,node_id_3@locator_3
```

Each entry binds a `node_id` to an address locator. The list is:

- Identical on every founding node (mismatches abort bootstrap with a loud error).
- Sized exactly `cluster_size` (mismatches abort bootstrap).
- Ignored after the first commit of the seed membership log entry; subsequent restarts of these same nodes proceed as normal joins.

The `node_id` fields here are *operator-assigned founding identifiers*, not the `uuid4()` runtime IDs. They serve only to map founding-member-slots to addresses at bootstrap time. After commit, the membership is keyed on the runtime `uuid4()` IDs of the founding processes.

### Bootstrap state machine

```
                            no --initial-members
                          ┌─────────────────────────────────────┐
                          │                                     │
                          ▼                                     │
                  ┌──────────────┐                              │
                  │  DISCOVERING │  resolve seeds, probe peers  │
                  └──────┬───────┘                              │
                         │                                      │
              any peer JOINED                                   │
                         │                                      │
                         ▼                                      ▼
                  ┌──────────────┐                       ┌─────────────┐
                  │  JOINING     │ ─────────────────────►│   JOINED    │
                  └──────────────┘  ADD committed via    └─────────────┘
                                    leader                       ▲
                                                                 │
                          --initial-members on launch            │
                                  │                              │
                                  ▼                              │
                          ┌──────────────┐                       │
                          │  FORMING     │ confirm peers, run    │
                          └──────┬───────┘ pre-vote at term 1   │
                                 │                               │
                            quorum confirmed                     │
                                 │                               │
                                 ▼                               │
                          ┌──────────────┐                       │
                          │ BOOTSTRAPPING│ propose seed log,    │
                          └──────┬───────┘ commit to majority   │
                                 │                               │
                                 └───────────────────────────────┘
```

### Bootstrap algorithm

1. Each founding node loads `--initial-members`, validates its own `node_id` is in the list, validates list size equals `cluster_size`.
2. Each founding node resolves the locators of the other initial members and TCP+mTLS handshakes them.
3. Handshake exchange: `BootstrapHello { my_node_id, cluster_id, role, initial_members_hash, runtime_uuid }`. The `initial_members_hash` is `sha256(sorted(initial_members))`. Receivers reject the handshake if their own hash differs.
4. Once a node has received valid `BootstrapHello` from a quorum of the initial set, it runs Raft pre-vote (AD-5) at term 1.
5. Pre-vote winner proposes the seed membership log entry: `EnterJoint { old_members: ∅, new_members: <runtime_uuids of founding set> }` at term 1.
6. On commit at majority, the winner proposes `LeaveJoint { members: <runtime_uuids> }`, completing the joint-consensus transition.
7. Same Raft transaction commits the `cluster_uuid` (newly minted `uuid4()`) and `cluster_size` as cluster state.
8. Bootstrap complete. The cluster is in `JOINED` state.

If any of the above fails (pre-vote timeout, conflicting `initial_members_hash`, unreachable quorum), the node exits non-zero with a structured error. The operator's process supervisor (or the operator) handles retry.

## 5. Join protocol (existing cluster)

A node without `--initial-members` (or whose initial-members list is rejected because the cluster has already formed) joins an existing cluster.

### Join algorithm

1. Node loads identity, generates `node_id = uuid4()`, resolves seeds.
2. For each candidate address, TCP+mTLS handshake. mTLS cert chain validated against cluster CA; cert subject role must match `--role` per AD-28 matrix.
3. Send `JoinHello { node_id, cluster_id, role, protocol_version, capabilities, advertised_address_hint }`.
4. Receive `HelloResponse { their_node_id, their_role, cluster_uuid, cluster_state, leader_hint, membership_epoch, current_membership_size, server_capabilities }`.
5. Validate:
   - `their.cluster_id == my.cluster_id` (else: wrong cluster, refuse).
   - `protocol_version` major matches (AD-25, else: refuse).
   - `their_role` is in the AD-28 allowed-source-role set for my role.
6. If `cluster_state == JOINED`, follow `leader_hint`. If the responder is the leader, proceed in-place. Otherwise open a connection to the leader.
7. Send `JoinRequest { node_id, role, advertised_address, capabilities, attestation }` to the leader.
8. Leader validates and proposes `AddLearner { node_id, role, advertised_address, capabilities, learner_added_at_epoch }` via Raft.
9. On commit, leader replies `JoinAccepted { cluster_uuid, current_membership, current_membership_epoch, cluster_size, fence_token }`.
10. Joining node enters **learner** state (Section 7), begins receiving snapshot + log via Raft InstallSnapshot + AppendEntries.
11. When learner's commit index is within `learner_promote_threshold` (default 256 entries) of leader, leader proposes `Promote { node_id }`.
12. On commit, joiner becomes a voting member. State transitions to `JOINED`.

### Advertised address resolution

The node's `advertised_address` (what peers use to reach it) is determined by:

1. If `--advertised-address` is set, use it (subject to reverse-probe verification in environments where peers can't trust client-asserted addresses).
2. Otherwise, accept the source IP of the incoming TLS connection during the leader handshake as the advertised address. This is the SOTA-default ("source-of-truth is what worked"), and avoids the failure modes of reverse-probing through asymmetric firewalls.
3. Reverse-probing is opt-in via `--verify-advertised-address` for environments where source-IP can be spoofed (rare in mTLS environments since the cert binds identity, but available for defense-in-depth).

Address changes mid-life (e.g., K8s pod recreation on a new host) are handled by full re-join with a new `node_id`, not by an in-place update. The old `node_id` is evicted via Section 8.

## 6. Membership log and joint consensus

The cluster's membership state is replicated via the cluster's existing Raft group:

- Gate cluster: global Raft (members spread across regions).
- Per-DC manager cluster: regional Raft (members within one DC).

Workers are not in any Raft group; their registration is handled in Section 12.

### Membership log entry types

All entries are versioned (Section 14) and include `(committed_at_term, committed_at_epoch)` metadata.

| Entry | Fields | Purpose |
|---|---|---|
| `EnterJoint` | `old_members`, `new_members`, `cluster_uuid_at_create` | Begin joint-consensus transition. Quorum requires majorities of *both* configurations. |
| `LeaveJoint` | `members` | Complete joint transition. Quorum now requires majority of new only. |
| `AddLearner` | `node_id`, `role`, `advertised_address`, `capabilities` | Add non-voting member receiving log replication. |
| `Promote` | `node_id` | Promote learner to voter. May trigger an `EnterJoint`/`LeaveJoint` pair if it changes the voting set. |
| `Remove` | `node_id`, `reason ∈ {leave, evict, force}` | Remove a member. Triggers `EnterJoint`/`LeaveJoint`. |
| `UpdateMetadata` | `node_id`, `metadata_delta` | Update non-identity metadata (capabilities, role-aware bracket settings, drain status). |
| `RegisterDatacenter` | `dc_id`, `manager_seeds`, `region_code`, `registered_at_epoch` | (Gate cluster only) Catalog a manager DC. |
| `ResizeCluster` | `new_cluster_size` | Operator-driven resize. Forces joint-consensus path. |

### Why joint consensus

Single-server membership changes are correct in the original Raft paper but only under the assumption that the cluster cannot suffer a partition during the change. In practice, single-step changes admit failure modes where a minority partition believes it has the new quorum:

- Cluster of 3 (A, B, C). Operator removes C. During the change, a partition isolates {A, B} from {C}.
- {A, B} thinks the new config is {A, B} (2-node majority is 2). It elects a leader and writes.
- {C} thinks the old config is {A, B, C}. It cannot make progress because it can't reach a majority.
- This is safe in this example, but a subsequent change while C is partitioned can transition into a configuration where C's stale view conflicts.

Joint consensus eliminates this entire class. During `EnterJoint`/`LeaveJoint`, any commit requires majorities of *both* configurations. Minority partitions cannot complete the transition because they lack one of the required majorities.

### Membership-generation fencing

Every cluster RPC carries a fence header:

```
ClusterRPCFence {
    cluster_uuid:          uuid              # bootstrap-minted, immutable
    membership_epoch:      u64               # incremented per committed membership change
    sender_node_id:        uuid              # runtime id of sender
    sender_term:           u64               # current Raft term as known by sender
    sender_membership_lsn: u64               # last membership entry sender has applied
}
```

Receivers validate:

| Check | Rejection reason |
|---|---|
| `fence.cluster_uuid != receiver.cluster_uuid` | `WRONG_CLUSTER` — zombie from destroyed cluster |
| `fence.sender_node_id ∉ receiver.current_membership` | `STALE_MEMBER` — sender was removed |
| `fence.sender_term < receiver.current_term` | `STALE_TERM` — sender is from an old leadership epoch (AD-10) |
| `fence.membership_epoch < receiver.membership_epoch - max_membership_lag` | `STALE_MEMBERSHIP` — sender's view is too far behind |

The fence is checked at the protocol layer before any handler runs. Rejected RPCs return a structured `ClusterFenceError` so the sender can self-correct (resync membership, refresh `cluster_uuid`, exit if zombie).

This is the AD-10 fence-tokens-from-terms idea extended along the membership axis. Together they eliminate the "stale node writing into the wrong cluster" failure mode.

## 7. Learner state and safe catch-up

When a new member is added via `AddLearner`, it does not vote and does not count toward quorum. The cluster size from a quorum-calculation perspective is unchanged.

### Learner lifecycle

```
                  AddLearner committed
                          │
                          ▼
                   ┌──────────────┐
                   │   LEARNER    │  receive snapshot + log
                   └──────┬───────┘
                          │
              commit_index within
              learner_promote_threshold
              of leader's commit_index
                          │
                          ▼
                   ┌──────────────┐
                   │  PROMOTING   │  leader proposes Promote
                   └──────┬───────┘
                          │
                  Promote committed
                  (joint-consensus
                   transition if voting
                   set changes)
                          │
                          ▼
                   ┌──────────────┐
                   │    VOTER     │  full member
                   └──────────────┘
```

### Why learners

A new joiner can lag the leader by gigabytes of state machine. If it became a voter immediately:

- It could be the deciding vote in an election but unable to actually replicate (would hold up commits).
- It could win an election (if it had a higher term) and roll back committed entries it never received.
- It could artificially expand the quorum size before having state, transiently making it harder to reach quorum.

Learner state is the SOTA solution: catch up first, promote later, vote never as a learner.

### Promotion threshold

`learner_promote_threshold` is the maximum log lag (in entries) at which a learner can be promoted. Default 256 entries; configurable per-cluster. Tuning:

- Lower threshold → promotion happens sooner after catch-up, faster cluster scale-up.
- Higher threshold → less risk of immediate slow follower, more headroom for replication transient slowdowns.

If a learner cannot catch up within `learner_max_lifetime` (default 30 minutes), the leader proposes `Remove { node_id, reason: evict }` — the joiner is too slow and is rejected. The operator's substrate restarts the process, generating a new `node_id`, and it tries again.

## 8. Failure detection: SWIM + phi-accrual hybrid

Two complementary detectors, both running:

### SWIM gossip (cluster-wide convergence)

Existing implementation (AD-27, AD-29, AD-30, AD-35, AD-46). Drives the cluster-wide view of who is alive, suspect, dead. SWIM events feed the **eventual** REMOVE proposal but never directly cause REMOVE — that path is Raft only.

SWIM transitions for an existing voter:

```
ALIVE ──Lifeguard suspicion bracket──► SUSPECT
SUSPECT ──multiple indirect probe failures──► DEAD
DEAD ──tombstone_retention (default 10min)──► REMOVE proposed via Raft
```

The 10-minute tombstone retention is deliberate. Transient network partitions are the common case; actual node death is the rare case. Service registries that evict aggressively (e.g., DNS TTLs of seconds) cause real production outages on every network blip. The SOTA bar (Linkerd, Istio) holds endpoints for minutes after they look dead, because real death is rare and brief blips are common.

### Phi-accrual (per-edge probabilistic detection)

Phi-accrual (Hayashibara et al., used in Cassandra, Akka, Hazelcast) computes a continuously-updated suspicion value φ per peer-to-peer edge:

```
φ(t) = -log10(P(heartbeat arrives by t | history))
```

Higher φ = higher confidence the peer is unreachable from *this* node. Threshold typically 8.0 for declaring failure; warning at 4.0.

Phi-accrual feeds:

- **Connection circuit breakers** (extending AD-18). High φ for a peer trips its circuit breaker; subsequent requests fail fast.
- **Per-edge routing decisions**. If φ to manager M from gate G is high, G routes jobs elsewhere even if M is still cluster-ALIVE from other gates' perspectives. This is the locality-aware piece of AD-36 hardening.
- **SWIM probe budgeting**. Edges with high φ get more frequent probes; healthy edges get fewer.

Phi-accrual uses AD-35 Vivaldi RTT estimates as the baseline expected inter-arrival time, so the detector adapts to network topology. Cross-DC edges naturally have higher baselines than intra-DC edges.

### Multi-stage eviction summary

```
Stage             Timer (default)         Trigger
─────────────────────────────────────────────────────────────────
ALIVE → SUSPECT    Lifeguard bracket       SWIM probe miss
SUSPECT → DEAD     ~10s                    indirect probe failures
DEAD → tombstone   instant                 cluster gossip convergence
Tombstone → Remove 10 min                  Raft REMOVE proposed by leader
```

The four-stage progression means a peer must be unreachable from the leader's perspective for ~10 minutes before being removed from membership. This is the "battle-tested" tolerance for blips.

Operator escape: `force-remove` (Section 13) skips the tombstone and proposes REMOVE immediately. Required for situations where the operator knows the node is gone (e.g., physical hardware destroyed) and wants the cluster to reform faster.

## 9. Watch streams for membership distribution

Every node opens a long-lived **watch stream** to the cluster (initially to a follower for load distribution; failover to leader for higher consistency). Watches replace polling.

### Watch protocol

```
WatchOpen {
    last_seen_membership_epoch: u64
    last_seen_lsn:              u64
    watch_filter:               { entry_types, node_id_subset }
    watcher_node_id:            uuid
}
```

Server response:

```
WatchSnapshot {
    snapshot_epoch:      u64
    snapshot_lsn:        u64
    membership_at_lsn:   list[MemberRecord]
    cluster_uuid:        uuid
    cluster_size:        u32
}
```

Then a stream of:

```
WatchDelta {
    epoch:       u64
    lsn:         u64
    entry:       MembershipLogEntry
    apply_after: lsn
}
```

### Reconnect semantics

On disconnect, client reconnects with `last_seen_lsn`. Server responds with either:

- `WatchDelta` stream from `last_seen_lsn + 1` if the LSN is within snapshot retention.
- A fresh `WatchSnapshot` if the LSN has rolled past retention (catastrophic disconnect).

The server maintains a bounded ring buffer of recent log entries (default 16384, configurable) to serve reconnects. Beyond that, clients re-snapshot.

### Why watches, not polls

Polling has p99 latency proportional to poll interval and load proportional to cluster size × poll rate × node count. Streams scale with churn rate, which is orders of magnitude lower in steady state.

This is the etcd watch / Envoy xDS / Linkerd Destination API pattern. It is the SOTA bar for control plane distribution.

## 10. Disconnected mode for the data plane

The control plane (cluster membership Raft) and the data plane (job execution) are separated by a soft-state cache. The data plane never blocks on the control plane.

### Soft-state cache

Every node maintains, in memory:

```
SoftStateCache {
    last_observed_membership: { node_id → MemberRecord }
    last_observed_epoch:      u64
    last_observed_at:         monotonic_ns
    cluster_uuid:             uuid
}
```

The cache is refreshed by the watch stream. Every consumer of cluster state reads from the cache, not directly from Raft.

### Staleness accounting

Every cache read returns `(value, staleness_ms = now() - last_observed_at)`. Consumers choose:

- **Hard-fresh required**: re-read via ReadIndex (Section 11), pays a round-trip.
- **Bounded staleness acceptable**: read cache if `staleness_ms < bound`, else re-read.
- **Best-effort**: always read cache, never block.

Most data plane operations are best-effort or bounded-staleness:

- Worker progress reporting → best-effort (cache).
- Manager workflow dispatch → bounded staleness (5s typical).
- Gate routing decisions → bounded staleness (10s typical).
- Cancellation propagation → hard-fresh (linearizable, AD-20).

### Behavior when the control plane is unreachable

When the watch stream is disconnected for longer than `disconnected_mode_threshold` (default 30s):

- Cache is still served, with growing `staleness_ms`.
- Workers continue executing in-flight jobs (AD-4: workers are source of truth for their workflows).
- Workers buffer progress updates locally up to `disconnected_buffer_ms` (default 5min) — drop telemetry-class messages first (AD-37 priorities).
- Managers continue accepting workflows from gates they have cached as ALIVE; AD-38 LOCAL durability tier preserves them.
- Gates continue routing to manager DCs they have cached as healthy; AD-36 routing uses cached DCRegistration.
- Job cancellation falls back to best-effort with retry on reconnect (AD-20 idempotency makes this safe).

When the watch reconnects:

- Buffered telemetry flushes (respecting AD-37 backpressure).
- Cache is refreshed; soft-state diverges are reconciled.
- Operations that were waiting on hard-fresh state proceed.

This is the Linkerd / Istio robustness pattern: control plane outage is not a data plane outage. The SLO target is that a 10-minute control plane partition causes no observable job execution failures, only delayed observability and routing-decision staleness.

## 11. Linearizable reads via ReadIndex

For any read that must be linearizable (e.g., "what is the current cluster membership at this exact moment?"), use the Raft ReadIndex protocol:

1. Reader (any voter) asks the leader for the current commit index.
2. Leader verifies it is still leader by exchanging heartbeats with a quorum (or relies on its current leader lease, see below).
3. Leader replies `(commit_index_at_read)`.
4. Reader waits until its local apply index reaches `commit_index_at_read`.
5. Reader serves the read from its local state machine.

No log entry is written for reads. Cost: one round-trip from reader to leader, plus the leader's quorum verification (which is batched across many concurrent reads).

### Leader leases

The leader optionally holds a lease for `quorum_timeout / 2`. While the lease is valid, the leader can answer ReadIndex requests without quorum verification (because it knows no other leader has been elected). On lease expiry, full quorum verification is required.

Leases require bounded clock skew, which Hyperscale does not assume in general. Therefore leases are opt-in via `--leader-lease-enabled` and require operator opt-in to bounded-skew (NTP available). When disabled (the default), full quorum verification is always performed; this costs one round-trip per ReadIndex but requires no clock-skew assumption.

### Stale reads from followers

Followers can serve reads with bounded staleness without contacting the leader. The follower's apply index is "behind by some amount" relative to the leader; the staleness bound depends on replication lag. AppendEntries throughput is the limiting factor; in steady state, lag is sub-millisecond.

## 12. Workers (not in Raft)

Workers do not form a cluster. They are ephemeral, high-churn, and explicitly exempted from consensus participation (AD-38). Each worker has a single owner manager; AD-48 disseminates worker state across managers within a DC.

### Worker join

1. Worker starts, generates `node_id = uuid4()`.
2. Resolves `--manager-seeds` (same locator system as Section 2).
3. Probes candidate managers using AD-28 weighted rendezvous + power-of-two-choices for load balancing.
4. Selected manager: TCP+mTLS handshake, exchange `WorkerHello { node_id, capabilities, advertised_address }`.
5. Manager validates (cluster_id, role per AD-28 matrix), accepts via *local* registration (no Raft entry).
6. Manager broadcasts `WorkerStateUpdate { node_id, owner_manager, state: REGISTERED, incarnation }` to peer managers via AD-48.
7. Worker is now functional.

### Why workers skip Raft

Worker fleets are 10-1000x larger than control plane clusters and churn 100-1000x more frequently (HPA scaling, per-test fleets, spot preemptions). Putting workers in Raft would:

- Bloat the membership log with high-frequency churn.
- Slow Raft apply by orders of magnitude.
- Make the control plane susceptible to worker-fleet incidents.

Instead, worker registration is **local to the owner manager** (in-memory + AD-38 LOCAL tier WAL for crash recovery within a pod) and **propagated** via AD-48 (TCP broadcast for critical events, gossip piggyback for steady state). This is the architectural separation called out in AD-38 ("workers never participate in consensus").

### Worker failure handling

- Worker SWIM-dies → owner manager detects via heartbeat timeout.
- Owner manager broadcasts `WorkerStateUpdate { state: DEAD }` to peer managers (AD-48).
- Workflows on that worker are reassigned via AD-4 / AD-31 leadership protocols.
- No Raft REMOVE is needed because there's no Raft entry to remove.

### Worker manager failover

If a worker's owner manager dies, the worker detects via SWIM (AD-7), drops the registration, and re-registers with another manager. AD-31 ensures job leadership for affected workflows transfers correctly.

## 13. Operational primitives

### Drain

```
POST /admin/drain
  → Node marks itself draining (UpdateMetadata Raft entry).
  → Leader stops routing new work (job dispatch, worker assignments) to this node.
  → In-flight work continues until completion.
  → Node sends LeaveRequest when drained.
```

### Force-remove

Operator escape for unresponsive members, gated by epoch:

```
POST /admin/force-remove?node_id=<id>&current_epoch=<epoch>
  → Leader validates current_epoch matches its membership_epoch.
  → Leader proposes Remove { node_id, reason: force } via Raft.
  → Skips tombstone retention; immediate removal on commit.
```

The `current_epoch` parameter is required and validated; this prevents the "operator removed the wrong node after the cluster churned" failure mode. If the epoch is stale, the request is rejected with the current epoch in the error, and the operator can retry.

### Membership freeze

```
POST /admin/freeze
  → Leader sets a freeze flag (UpdateClusterMetadata Raft entry).
  → All membership change proposals (AddLearner, Promote, Remove) are rejected with FROZEN error.
  → Useful during maintenance windows or while debugging.

POST /admin/unfreeze
  → Clears the flag.
```

### Snapshot export/import

```
POST /admin/snapshot/export
  → Returns a tarball: { cluster_uuid, membership_epoch, raft_state, soft_state }.
  → Used for disaster recovery and audit.

POST /admin/snapshot/import (only on a freshly-launched cluster)
  → Validates the cluster has no committed state.
  → Imports the snapshot; mints a NEW cluster_uuid (prevents accidental fork).
  → Logs a structured event noting the import source.
```

Import always mints a new `cluster_uuid` so an imported cluster cannot be confused with the original. This prevents the "I restored a snapshot and now have two clusters with the same identity" failure mode.

### Read-only mode

```
POST /admin/read-only
  → Cluster refuses all writes (membership changes, job submissions, etc.).
  → Reads continue.
  → Used during upgrades and dangerous maintenance.
```

## 14. Schema versioning

Every Raft log entry carries a schema version prefix:

```
LogEntry {
    schema_version: u32
    entry_type:     u32
    payload:        bytes (versioned encoding)
}
```

The apply layer dispatches on `(entry_type, schema_version)`. Old schemas remain supported until a configurable retention (default: two major releases). Forward compatibility (unknown fields ignored) is per AD-25.

### Schema migration

When a new field is added to an entry type:

1. Define schema version `N+1` that includes the new field.
2. Apply layer supports both `N` and `N+1` simultaneously.
3. Writers emit `N+1`.
4. After all nodes are on the new version (negotiated via AD-25 capabilities), writers may continue emitting `N+1`.
5. After retention window, support for `N` can be removed.

This is the standard SOTA approach (etcd v3 schema, CockroachDB versioned migrations). Hyperscale piggybacks on AD-25's protocol versioning for transport-level compat and adds explicit Raft-log schema versioning for state-machine compat.

## 15. Determinism boundary

The Raft state machine **apply layer** is a hard determinism boundary. Violations cause divergence between followers (different state machines from the same log = catastrophic).

### Determinism rules (enforced at apply layer)

- **No wall clock.** `time.time()`, `time.time_ns()`, `datetime.now()` are forbidden in apply code. Time-like inputs come from HLC timestamps embedded in log entries (AD-38).
- **No randomness.** `random.random()`, `os.urandom()` are forbidden. If randomness is needed, the seed must be in the log entry.
- **Sorted iteration over maps and sets.** Python's `dict.items()` ordering is insertion-order but iteration over `set` is not stable across Python versions or platforms. Apply code uses `sorted(d.items())` and `sorted(s)`.
- **No filesystem reads.** Apply layer has no I/O.
- **No network calls.** Apply layer has no I/O.
- **No hash-based identity.** Hashes of objects, addresses, etc. are non-deterministic across runs. Use explicit IDs.

These rules are enforced by:

- **Static lint rule** (custom Ruff plugin) that flags forbidden imports/calls in `cluster/state_machine_apply.py` and related modules.
- **Runtime assertion** in test mode that runs apply with two random seeds and compares output (chaos test catches non-determinism).
- **Code review checklist** for any change to apply code.

This is the Jepsen-clean bar. Without it, Raft followers will silently diverge on rare inputs and the cluster will be quietly broken.

## 16. Throughput primitives

### Group commit on the Raft WAL

Following AD-38's NodeWAL pattern, the Raft log writer:

- Collects pending log entries from concurrent proposals.
- Batches into a single `write() + fsync()` call.
- Resolves all proposers' futures after fsync completes.

Throughput: at 500μs fsync latency, ~2000 batches/sec × 100-1000 entries per batch = 200K-2M entries/sec.

### Pipelined AppendEntries

Leader sends AppendEntries(N+1) before AppendEntries(N) is acknowledged. Per-follower in-flight window bounded by `max_inflight_appendentries` (default 256). Slow followers don't block the pipeline because each follower has an independent window.

### Flow control

Per-follower flow control: if a follower's in-flight window is saturated, the leader stops sending until ACKs free space, but other followers are unaffected. This prevents a single slow follower from stalling the cluster.

### Snapshot streaming

When a follower (or learner) falls too far behind, the leader sends a snapshot via `InstallSnapshot` instead of replaying the log. The snapshot is chunked and streamed; the receiver applies it directly to the state machine, skipping the log.

Snapshots are taken periodically (every `snapshot_interval_entries` log entries, default 10000) on each member independently. Snapshots are local (not gossiped) and used only for self-recovery and learner catch-up.

### Read concurrency

Reads via ReadIndex (Section 11) do not write the log and do not block writes. Read throughput is decoupled from write throughput. A read-heavy workload scales by adding followers.

### Performance targets

| Metric | SLO | Mechanism |
|---|---|---|
| Membership change commit (steady state) | p50 < 5ms, p99 < 50ms | Group commit, pipelined AppendEntries |
| Membership change commit (cross-region) | p50 < 100ms, p99 < 300ms | Pipelining hides round-trip cost |
| ReadIndex read | p50 < 2ms (intra-DC), p99 < 10ms | Lease (if enabled) or batched verification |
| Watch delta propagation | p50 < 5ms, p99 < 50ms after commit | Server-side dispatch on apply |
| Cold-cluster bootstrap | p99 < 10s | DNS resolution + 1 Raft round-trip |
| New-member join + learner-promote | p99 < 30s for 100MB state | Snapshot streaming |
| Failure detection (intra-DC) | < 5s to SUSPECT, < 15s to DEAD | SWIM + phi-accrual |
| Failure detection (cross-DC) | < 15s to SUSPECT, < 45s to DEAD | AD-35 role-aware brackets |
| Membership eviction (tombstone) | 10 min default | Configurable; tradeoff between blip tolerance and stale routing |

## 17. Multi-DC federation

The control plane is hierarchical:

- **Global gate cluster**: one Raft group, members spread across regions (e.g., 5 gates across 3 DCs). Hosts the global job ledger (AD-38), DCRegistration entries, idempotency state, cross-DC routing state.
- **Per-DC manager cluster**: one Raft group per DC (typically 3-5 managers). Hosts local workflow state, AD-31 job leadership, AD-48 worker state propagation.
- **Workers**: not a cluster (Section 12). Registered with one owner manager per worker.

### DCRegistration

Each manager cluster registers itself with the gate cluster on startup. The manager leader proposes (via gate Raft):

```
RegisterDatacenter {
    dc_id:                       string
    manager_seeds:               list[Locator]
    region_code:                 string
    advertised_endpoint:         address
    cluster_uuid_of_dc:          uuid
    registered_at_gate_epoch:    u64
}
```

The gate cluster's Raft state contains the catalog of known DCs. Gates discover DCs from their own Raft state, monitor them via FederatedHealthMonitor (AD-33), and route jobs via AD-36 / AD-51. Gates are not Raft members of any manager cluster.

### DC re-registration on regeneration

When a DC's manager cluster suffers catastrophic quorum loss and is rebuilt, the new cluster has a new `cluster_uuid_of_dc`. On re-registration:

- Gate cluster sees a `RegisterDatacenter` with a different `cluster_uuid_of_dc` than the existing entry.
- The entry is **versioned**, not overwritten. A new generation marker is appended.
- Routing components (AD-36, AD-45) treat the epoch bump as "new generation, drop learned state for this DC" — Vivaldi coordinates re-learned, EWMA reset, route stickiness invalidated.
- Old DCRegistration is retained for `dc_registration_grace_period` (default 1h) so in-flight references can fence-validate against the old epoch before failing.

This is the "robustness of battle-tested service registries" pattern: never silently overwrite registrations across generations, always make the transition observable.

### Bootstrap order

1. Gate cluster forms first (using `--initial-members` per Section 4).
2. Per-DC manager clusters form (each using its own `--initial-members`).
3. Each manager cluster's leader calls `RegisterDatacenter` into the gate cluster after its own bootstrap completes.
4. Workers join their owner manager (Section 12).

If a manager cluster bootstraps before the gate cluster is reachable, it waits in a `WAITING_FOR_GATES` state, retrying with backoff (AD-21 jitter). Workers behind that manager cluster wait for their managers to be reachable; AD-21 jitter prevents thundering herds on gate recovery.

## 23. Open questions

The following are deliberate non-decisions, flagged for future resolution:

1. **`--initial-members` operator UX.** The list must be identical across founding nodes. Options: (a) operator types it on every node (error-prone but explicit), (b) Hyperscale provides a CLI tool that generates the list from a seed-list-at-bootstrap-time (operator runs once, copies output), (c) auto-generated and stored in a shared config object (defeats the "no external coordination" principle if taken too far). Leaning toward (b) — a tool, not magic.

2. **Leader lease semantics.** Enabled-by-default requires bounded clock skew; disabled-by-default costs one round-trip per ReadIndex. Cost is acceptable for control plane reads (few QPS); enabled-by-default may matter for very high-frequency data-plane reads. Leaning toward disabled-by-default with explicit operator opt-in.

3. **Snapshot import policy.** Should snapshot import require the new cluster to be freshly bootstrapped with the same `cluster_id` as the snapshot's source? Or should it always mint a new `cluster_uuid` regardless? The latter is safer (cannot accidentally fork); the former enables operators to "restore in place." Leaning toward latter.

4. **DCRegistration history depth.** How many generations of a DC's registration should the gate cluster retain? Each adds storage but improves debuggability. Default 3 generations, configurable.

5. **Phi-accrual threshold per role.** Phi=8 is the Cassandra default. Roles may benefit from different thresholds: workers under extreme load may need higher (slower to declare failure); cross-DC gates may need lower (faster to circuit-break). Probably defer until real load data is available.

6. **Watch fan-out at scale.** A 1000-worker cluster with each worker watching the manager-cluster generates 1000 watch streams. Followers can serve watches to distribute load, but this needs measurement. Mitigation if needed: hierarchical watch proxying (gates serve watches to their workers' managers, managers serve to their workers).

## Summary

AD-52 specifies a single cluster formation and membership protocol that runs on every reasonable deployment substrate, requires zero persistent storage, and meets state-of-the-art consensus-database and service-registry standards. The protocol is built on Hyperscale's existing primitives (Raft, SWIM, AD-28 discovery, AD-38 ledger, AD-46 IncarnationTracker) and extends them with:

- Deterministic bootstrap via explicit `--initial-members`.
- Joint consensus, learner state, and membership-generation fencing for safe membership changes.
- SWIM + phi-accrual hybrid for accurate failure detection.
- Watch streams for efficient membership distribution.
- Disconnected mode for data-plane resilience.
- Apply-layer determinism guarantees.
- Comprehensive operational primitives and observability.

The non-negotiables for correctness (Phase 1) are joint consensus, learner state, and fencing. Without these, the cluster admits failure modes that violate consensus safety. Phase 2 (robustness) and Phase 3 (operations/performance) are required to meet the SOTA bar but can be staged.

The module lives at `hyperscale/distributed/cluster/`, extends existing `raft/`, `swim/`, `discovery/`, and `server/protocol/`, and introduces no external dependencies beyond OS-level name resolution.
