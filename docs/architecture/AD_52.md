Section 10, disconnected mode (2026-10, decided with the user): a worker
whose job leader SWIM declares dead does not keep executing indefinitely --
the cluster re-queues a lost worker's workflows elsewhere, and running
both copies would double the load -- but it no longer gives up after a
fixed 5s either. The orphan grace is derived from the cluster's own
timings (`derive_orphan_grace_seconds`: the managers' worst-case
suspicion window, a leader election and the transfer's request -- 44s by
default), raised to the longest rescue the worker has seen (a transfer or
leadership claim arriving after the orphaning), and extended by AD-26's
decaying grants (`EXTENSION_MIN_GRANT`, `EXTENSION_MAX_EXTENSIONS`) while
manager heartbeats keep reaching the worker -- a cluster that can still
take the job over. An isolated worker, hearing no manager, cancels when
the grace ends. A manager claiming the job's leadership clears the orphan
even when it is the leader the workflow had (a false death no longer
cancels work its live leader still leads). Final results the worker could
not deliver are kept until delivered: attempts run only while a manager
is reachable, bounded by `WORKER_RESULT_MAX_RETRIES` and
`WORKER_PENDING_RESULT_LIMIT`; the 300s `WORKER_RESULT_TTL` that dropped a
long-isolated worker's output is gone. Progress was already safe: reports
are cumulative, so the next supersedes any lost.

The soft-state cache (2026-10, scoped with the user: watch-fed): a
`ClusterViewCache` holds a cluster's membership as last observed -- holders,
cohort, voters and learners, mode, applied index -- folded from the watch
(section 9) by a `ClusterWatchFollower`, which polls one member until it
fails, then the next, and once none answers waits one poll's wait before
going round again (an unreachable cluster never spins it). A read returns
the view with its staleness, dated from when the poll that brought it was
sent; a healthy watch never lets it age past two polls (each its wait plus
the request's budget), so a staleness past that bound is disconnected mode
-- the view still served, its staleness growing -- with no fixed 30s.
Consumers: each gate follows every datacenter it knows (at boot, and on
`hyperscale join`), and a watched cohort change becomes its routing lists
-- a manager a resize adds is registered with, one it removes is forgotten,
here and in the joined-peer store a restart would reconnect from; each
worker follows its datacenter, and the cohort becomes its rejoin seeds.
Linearizable reads keep going through ReadIndex (section 11); routing and
rejoin take the cached view as is. The membership VOPR's operator watch is
this follower and cache (a cache that drops releases fails 17 of its
tests); tests/unit/simulation/sim/test_cluster_watch_follower.py proves the
disconnection bound (exact, never early) and the no-spin pause (removing it
spins the loop); tests/integration/cli/test_cli_gate_follows_manager_resize.py
proves a resize reaches a gate. Verified by
`tests/unit/distributed/worker/test_worker_orphan_grace.py`,
`test_worker_orphan_reclaim.py` and
`test_worker_result_kept_until_delivered.py` (each mutation-checked or
failing on the code it replaced).

Section 2, seed locators (2026-10): a cohort flag (`--managers`/
`--manager-udp`, `--gates`/`--gate-udp`) takes locators as well as
addresses -- `tcp://`, `dns://name:port` (every A/AAAA record),
`dns-srv://_service._proto.name`, `file:///path` and `exec:///path` (one
locator per line, of the first three kinds: no nesting). Listing paths are
checked as this section requires (absolute, owned by this user, no
directory above writable by everyone; refused on Windows, which has no such
ownership model). As built, a cohort resolves once, at launch, not on an
interval: it fixes the quorum floor, which only a committed resize changes
after. Locators therefore require `--cohort-size`, the size every founder
agrees on (section 1): resolution repeats every formation interval until it
yields exactly that many members with this node among them, or fails the
boot at --boot-timeout -- a Kubernetes headless service publishes only
ready pods, and a pod that resolved itself alone would otherwise found a
cluster of one beside the real one. TCP and UDP resolutions pair by host
(answer order is not stable), members sharing a host by ascending port. Nodes whose resolutions differ hold
different cohort digests and refuse each other: formation stalls, it never
splits. `--max-seed-candidates` sampling is not built: a cohort is never
sampled. Verified by `tests/unit/commands/test_seed_locators.py` (real
filesystem, processes and name resolution) and
`tests/integration/cli/test_cli_seed_locators.py` (three managers form from
`file://` locators; a wrong cohort size refuses to boot).

Section 14, log schema versioning (2026-10): every `RaftLogEntry` carries a
`schema_version`; a build reads a range (`RAFT_LOG_SCHEMA_VERSIONS`, today
1-1). Followers report the newest they read in every AppendEntries answer;
a leader writes the newest every member it replicates to reads -- the
oldest it writes until every member has reported -- so a rolling upgrade
never writes what a member on the older build cannot apply. A member
handed an entry outside its range anyway stops applying there (every entry
after it too) and logs where, never skipping it: a skipped entry would fork
its state silently. The membership group refuses a joiner that reads less
than it writes (`ClusterJoinRequest.schema_version`), and membership gates
every job group, so no group takes such a node in. Verified by
`tests/unit/distributed/raft/test_raft_schema_versions.py` (mixed builds
write the older schema, upgraded ones the newer; a member stops at an
unreadable entry and applies nothing after it -- each mutation-checked).
The upgrade procedure: run every node on the new build (which still reads
the old schema), and the cluster moves to the new one on its own.
Section 13's drain, force-remove, membership freeze and read-only mode are
built -- below; its snapshot export/import is not the design (below).

Section 9, watch streams (2026-10): `cluster_watch`, a long poll any
member answers from its applied membership log -- at once with the changes
after the watcher's index (claims, releases, mode, resizes, configurations,
in commit order), else when one is applied or the watcher's wait passes
(`CLUSTER_WATCH_WAIT_SECONDS`, 25s: with the transport's 5s it stays under
the shortest common proxy timeout). A watcher of another cluster (founded
anew) or behind the member's log compaction gets a snapshot to resume
from: the Raft log itself is the reconnect buffer, so there is no ring
buffer to size. A member behind the watcher answers nothing new and hands
back the watcher's own index -- switching members never replays. Watch and
status reads are telemetry priority (AD-37): a long poll holds its slot for
the wait and must never crowd out control traffic. `hyperscale cluster
--node <member> --watch` prints a snapshot and every change until Ctrl-C.
Verified by `tests/unit/simulation/sim/test_cluster_membership_vopr.py`: a
watcher polling a random member each time through the whole fault window
-- crashes, refoundings, partitions -- never sees an event twice or out of
order, always holds the state the members applied at the index it
reached, and ends on the final state; mutation-checked (a lagging member
handing back its own index replays; dropping releases diverges). E2E:
`tests/integration/cli/test_cli_cluster_resize.py` watches a resize and the
new manager's claim. The spec's per-node watch of a soft-state cache feeds
section 10, which is not built.

Section 11, ReadIndex (2026-10): `RaftNode.read_index` (Raft thesis 6.4).
A leader that has committed an entry of its own term notes its commit
index, opens a read round, and sends heartbeats carrying it
(`AppendEntries.read_round`, echoed in the response); the read is
confirmed once a quorum of voters has answered that round or a later one
-- an answer to a heartbeat sent before the read began proves nothing --
and fails if leadership is lost or no quorum answers within the proposal
timeout. Reads arriving together share a round; nothing is written to the
log. A leader that is its own quorum confirms at once. `cluster_status`
(`hyperscale cluster --node <member>`) serves the membership -- leader,
voters, learners, cohort, holders, mode -- from the leader after a
ReadIndex, as of the index it has applied (at least the read index); a
member that is not the leader passes the request on once. Leader leases
are not built: the spec makes them opt-in under bounded clock skew, which
the default never assumes. Verified by
`tests/unit/simulation/sim/test_cluster_membership_vopr.py`: status reads
through random members throughout the fault window (partitions both ways
and one way, crashes, resets) are checked for linearizability -- never a
read index behind a commit the cluster made before the read was sent,
always the state every member applied at it; mutation-checked (a
read_index that skips confirmation serves a deposed leader's stale read).
E2E: `tests/integration/cli/test_cli_cluster_resize.py` reads the resized
cohort at once.

`ResizeCluster` (2026-10): the cohort -- which addresses may hold
membership, and so the quorum floor -- is replicated state of the
membership group, changed by a `cluster_resize` entry that adds or removes
exactly one address (`hyperscale resize --node <member> --add|--remove
<host:port>`).

- **One address per change.** A majority of a cohort of n and a majority of
  a cohort one address larger or smaller always share an address, and an
  address holds one process. So processes still launched with the cohort
  before a resize and processes launched with the one after can never
  hold two quorums at once -- not even when every process restarts
  together and refounds (the simulation below builds that). A two-address
  jump loses this: built as a mutation, the same scenario splits.
- **At most one resize behind.** Each process is launched with a cohort
  (its `--managers`/`--gates`); hellos and joins are accepted from the
  cohort the cluster holds and the one before it, so members not yet
  relaunched keep rejoining. The leader refuses a resize unless it and
  every voter that answers -- a quorum of them -- run launched with the
  cohort the cluster holds: after each resize, relaunch every member with
  the new cohort (each drains as it stops), then resize again.
- **Applying it.** Every member takes the new cohort (kept for its
  process's life, through any refounding), drops holders of addresses no
  longer in it -- the leader's reconciliation then removes them -- and
  sets every Raft group's quorum floor to its majority
  (`RaftNode.set_cohort_size`: a local floor, safe because a majority of a
  configuration's voters already intersects every other). The node's
  other quorums follow: the manager leadership quorum and SWIM election
  size, the gate cluster size, the AD-39 clock fence and its probe peers,
  and the floor of job groups founded later. A node whose address left the
  cohort neither joins nor founds. Refused while the cluster is frozen or
  read-only; the leader never removes its own address (stop it first).
- **Verified by** `tests/unit/simulation/sim/test_cluster_membership_vopr.py`:
  growing (cohorts 3 and 4) -- the new process joins, a second resize is
  refused until the old members are relaunched, and the cluster converges
  on every process holding the new cohort; shrinking (4 and 5); and a
  resize followed by every process restarting at once with a random part
  of the old members already relaunched (3, 4, 5) -- never two clusters
  able to commit. Twenty seeds each; mutation-checked (the rollout check
  removed; a two-address resize). E2E:
  `tests/integration/cli/test_cli_cluster_resize.py`.

Section 13, drain and force-remove (2026-10): both release a member's
address through the membership group's log (`cluster_leave`, control
priority); the leader's reconciliation then removes the member, as it
does for one silent past the tombstone retention -- without the wait.

- **Drain.** A manager or gate stopping gracefully (`stop`, or an operator
  Ctrl-C/SIGTERM of `hyperscale run manager|gate`, before the abort and
  bounded by --shutdown-timeout) asks its group to release its own member
  id (`ClusterMembership.leave`); a member that is not the leader passes
  it to the leader once. Only that member id is released, never a newer
  process at the address. A drain that fails is reported and the stop goes
  on: the leader's silence detection releases the member later.
- **Force-remove.** `hyperscale remove --node <member> --member <host:port>`
  releases whoever holds that address. The leader first greets it and
  refuses while the holder answers (a live member would claim its address
  again; a live one drains when stopped). A member that is not the leader
  answers with the leader instead of forwarding -- greeting a silent
  address can take a whole request timeout, which a forwarding hop of the
  same timeout would cut off -- and the CLI asks the leader once. Its
  budget per node asked: the tier's standard TCP timeout plus a formation
  interval (the release's proposal timeout).
- **Freeze and read-only.** The cluster's mode -- `open`, `frozen`,
  `read-only` -- is a log entry (`cluster_mode`; the command is the mode,
  so a repeated request changes nothing) applied by every member and
  carried in snapshots. Not open, no membership change commits: the leader
  neither reconciles its configuration nor releases silent members, and
  refuses joins, drains and force-removes. Read-only also refuses job
  submissions on that tier's managers or gates (not retryable: the
  operator's intent reaches the client at once); jobs already admitted go
  on. Set with `hyperscale membership --node <member> --mode
  open|frozen|read-only` (a non-leader passes it to its leader once). A
  cluster founded anew -- after the last one could no longer commit --
  starts open: the mode belongs to a cluster, and an inoperable one cannot
  hold anything.
- **Snapshot export/import: not the design.** The membership group's state
  is who holds each address and the mode -- what formation rebuilds from
  the live processes in a few rounds; restoring it onto other processes
  would name members that do not exist. Job state is each node's own
  ledger (AD-38), recovered from its disk where it has one.
- Verified by `tests/unit/simulation/sim/test_cluster_membership_vopr.py`:
  frozen, a member dead for twice the tombstone retention stays a voter and
  a drain is refused, then opened the cluster converges (cohorts of 3 and
  5, twenty seeds; mutation-checked: reconciling while frozen fails); and
  with the production tombstone retention (600s) and a ten-round window,
  drained and force-removed members leave the configuration and a live
  member's force-remove is refused, cohorts of 3 and 5, twenty seeds
  (mutation-checked: an acknowledged release that never commits, and a
  remove that skips the liveness greeting, each fail); and drains and
  removes right after faults heal keep every safety invariant. E2E (real
  processes): `tests/integration/cli/test_cli_cluster_departures.py`.

Slice B built (2026-10): per-job groups change membership only through
their logs.

- **Agreed initial voters.** A job's group is founded by the job's
  creator -- a manager admitting the job, a gate accepting it -- with the
  members live there (`current_members`). The voters travel to every
  member that joins the group: a manager's leadership announcement and
  job-state sync (`raft_voters`), a gate job's replica (`raft_voters`).
  A group is never created any other way: an incoming RPC does not create
  one, and the ledger replicator replicates only through a group that
  exists (it founded one with whatever members it knew, which no other
  member joined, so nothing it appended committed).
- **Leader-driven change.** Each tick, a group's Raft leader moves its
  configuration toward the cluster's live members
  (`RaftNode.reconcile_membership`): a voter no longer live is removed --
  unless fewer live voters would remain than the quorum floor, a change
  that could never commit -- a live non-member joins as a learner, and a
  learner holding every committed entry is promoted; one joint change at
  a time. Members only update their address books -- from SWIM's join
  and leave events in slice B, from the committed cluster membership
  since slice C (part 2 below); a member joining at an address an older
  incarnation held supersedes it. A member leaving a configuration stops being
  replicated to, and the leader drops its replication progress.
- Verified by `tests/unit/simulation/sim/test_raft_membership_vopr.py`
  (now driven by the production reconciler), and
  `tests/unit/simulation/sim/test_manager_job_group_membership.py` (real
  managers: every member holds the leader's voters; a manager restarted
  mid-job rejoins as a voter through the group's log, its old incarnation
  removed).

### Slice C (2026-10): the cluster membership group

Built (2026-10): `ClusterMembership` (`hyperscale/distributed/cluster/`),
the membership group itself, verified under simulation (part 1), and wired
into managers and gates (part 2, below).

One Raft group per cluster -- a datacenter's managers, or the gate tier --
whose configuration IS the cluster's membership. It is what lets a cluster
grow and shrink at runtime: a manager or gate joins as a learner and votes
once promoted; a member dead past its tombstone retention is removed.

**The cohort.** Only the configured cohort -- each node's configured peers
and itself -- are members; the cohort's digest travels in every greeting
and join, and a mismatch is refused. Every quorum needs at least a majority
of the cohort (AD-3), and each cohort address holds one process at a time,
so no two groups can ever both hold a quorum of live members. That is what
makes it safe to found a cluster without storage -- and to found it again
when the last one can no longer commit.

**Persistence (D1, `docs/architecture/D1_RAFT_PERSISTENCE.md`).** Storage
is used where a node has a disk it can trust, never relied on. A node's
`RaftStore` keeps its identity (node id with its start time, its
participation) and every Raft group's term, vote, log and snapshot, each
durable before any answer that depends on it. A node whose disk holds its
own intact store resumes as the same member of the same groups
(`member_resumed`); an empty disk joins as a new member; a disk it cannot
trust is set aside, unread, and the node joins as new. So a datacenter
whose managers all lose power comes back as the same cluster -- no
refounding, no regenerated datacenter at the gates -- and a REGIONAL
ledger commit is on a majority of the managers' disks. Without a disk,
everything below holds as before. Growing or shrinking the cohort itself
is the operator-driven `ResizeCluster` (section 6).

**Member ids.** `{node_id}@{host}:{port}#{participation}`: the process
incarnation's id (`NodeId.full` embeds its start time), the TCP address it
is reached at (so the address book travels with the configuration), and
how many times this incarnation has left a group. A member that came back
under its old id would be a voter that lost its votes and its log -- one
that can elect a leader missing entries it vouched for -- so leaving a
group always moves the node to a new participation.

**Formation (cold start).**

1. Each round a node greets every founder (`ClusterHello`); each answer is
   the process at that address now: discovering (no group), forming (a
   founding not yet committed), joining, or formed -- with its cluster's
   uuid, founding voters and leader.
2. A formed cluster is joined, never formed beside (the one most founders
   answer for).
3. Otherwise, once a quorum of the cohort answered as discovering and no
   founding is under way, the lowest-addressed discovering founder that
   could itself see such a quorum (or has not run a round yet -- a founder
   that cannot see a quorum never blocks one that can) proposes a founding
   (`FoundCluster`): those founders' member ids under a new cluster uuid.
   Each founder adopts the first founding offered to it that names it, and
   only that one. A founding commits only through Raft, with a quorum of
   its voters that is also a majority of the cohort: however many
   foundings were proposed, at most one commits. Two founders whose rounds
   overlap within a greeting's round trip may both propose; the one fewer
   than a quorum adopted is abandoned at once.
4. A founding that has not formed after a round, and fewer of whose voters
   still confirm it than its quorum, is abandoned.

**Joining.** Through the group's leader, which first greets the joiner's
address -- the claim must come from the process there now: a delayed
request of a process gone would unseat the live holder -- and then
commits the joiner's claim of that address (`cluster_claim_address`).
Every member applies the claims in the same order; the latest claim of an
address holds it.

**Membership changes.** The group's Raft leader reconciles its
configuration each tick (`RaftNode.reconcile_membership`) toward the
holders of the addresses. A holder that has not answered the leader for
the tombstone retention -- unreachable from the leader's perspective,
section 8 -- has its address released through the log
(`cluster_release_address`), so no later leader adds it back; the process
there claims the address anew if it ever answers again. The leader's own
view is the evidence, not SWIM's: SWIM reports addresses, by events a new
leader never saw, and a restarted process without storage restarts its
incarnation numbering -- the leader knows exactly which member has not
answered it, and since when (`RaftNode.silent_members`).

**Log compaction.** The group outlives every process in it, and
`RaftLog` refuses entries past 50,000 -- a cluster whose log filled would
freeze its membership. Its log is compacted through what it applied (Raft
section 7, `RaftNode` with `SnapshotManager`), etcd's way: a snapshot once
`CLUSTER_SNAPSHOT_ENTRIES` (10,000) were applied since the last, keeping
the `CLUSTER_SNAPSHOT_CATCH_UP_ENTRIES` (5,000) before it in the log, so a
member or watch that far behind catches up from the log. (Compacting after
every applied entry, as first built, left every watch nothing but
snapshots -- found by the resize E2E's watch -- and sent a full snapshot to
any member one entry behind.)
the snapshot carries the state (who holds each address) and the
configuration in force at its point, and a member the compaction point
passes by -- one that joins later, or falls behind a new leader -- is sent
it (`InstallSnapshot`). Installing keeps the entries after the snapshot
point only when the member holds the snapshot's last entry; otherwise its
whole log goes.

**A cluster that can no longer commit.** A cluster that lost a quorum of
its voters -- processes gone along with their disks, or never had any --
can never commit again -- not even
the change that would replace them. A formed member whose group has not
been operable for a round (`RaftNode.last_quorum_contact`) runs formation
rounds again, and leaves the group -- its members then found the cluster
anew -- once either:

- the answers prove it can never commit: a process other than the voter
  answers at the addresses of so many voters that the rest are no quorum;
- it has been inoperable longer than the tombstone retention: the members
  it waits on no longer hold the cluster back, just as the leader of an
  operable cluster would have removed them.

**CheckQuorum (Raft thesis 6.2).** A `RaftNode` leader that no quorum of
voters answered steps down. Members refuse votes while they hear from a
live leader (leader stickiness); without CheckQuorum a leader whose
heartbeats still reached its followers, but whose followers' answers did
not reach it, kept every follower refusing votes while it could commit
nothing -- for as long as that asymmetric partition lasted, in every Raft
group. The window is the transport's request timeout plus an election
timeout: a member's requests go one at a time, so a reachable member can
go unheard for as long as one lost request takes to time out. Measured on
the membership VOPR (twenty seeds per cohort size, TCP retransmission
delays): an election timeout alone deposed healthy leaders -- 21-23
leaderships per run against 11 -- and no CheckQuorum at all left 5-7
seeds per profile unconverged. It is also what `last_quorum_contact`
reports.

**Verified by** `tests/unit/simulation/sim/test_cluster_membership_vopr.py`:
cohorts of 3 and 5, twenty seeds each -- staggered starts, crash-restarts
under new node ids from inside one election to past the tombstone
retention, partitions both ways and one way only, shorter and longer than
it, connection resets, TCP retransmission delays -- checking vote safety,
election safety and state machine safety per cluster (entries, and the
state at each applied index: snapshots install state, not entries),
acknowledgment durability (no member id holds fewer committed entries
than it acknowledged), at most one cluster able to commit at once, no
handler raising and no loop dying; then convergence once faults heal: one
cluster, its voters exactly the live processes -- also with a machine lost
for good, whose address the leader releases. Without faults, exactly one
founding commits, for simultaneous and staggered starts. The runs replay
identically per seed. It catches a quorum floor counted over a founding's
voters rather than the cohort (split brain), a member rejoining under its
old participation (acknowledgment durability), an install that does not
restore the snapshot's state, and releases that do not apply.
`tests/unit/simulation/sim/test_raft_check_quorum.py` builds the asymmetric
partition (it fails without CheckQuorum);
`tests/unit/distributed/raft/test_raft_snapshot_install.py` builds a member
behind a configuration change and a deposed leader's conflicting entries
(each fails if an install keeps the member's own configuration, or keeps
entries after a snapshot entry it never held).

**Part 2, wiring.** Every manager and gate runs a `ClusterMembership` for
its tier -- a datacenter's managers, the gate tier -- founded by its
configured peers and itself (`--managers` / `--gates`), over six TCP
actions (`cluster_hello`, `found_cluster`, `cluster_join`,
`cluster_raft_request_vote`, `cluster_raft_append_entries`,
`cluster_raft_install_snapshot`), all control priority (AD-37). Every job
group takes its members from the committed membership
(`ClusterMembership.node_addresses`): the voters a job's creator founds its
group with, the members its leader reconciles it toward, the address book
-- SWIM's join and death events no longer edit Raft membership. So a job
is admitted only once its tier's membership has formed (the manager and
the gate refuse with a retryable error before), and a manager resumes the
jobs its ledger recovered the moment its membership forms. AD-39 clock
probing measures the configured peers, one entry per address, from boot.
Settings: `CLUSTER_FORMATION_INTERVAL_SECONDS` (1s: one round per SWIM
probe period) and `CLUSTER_TOMBSTONE_RETENTION_SECONDS` (600s, section 8).
Raft fixes the wiring surfaced: a leader that is its own quorum now commits
its term-start entry at once (a one-manager datacenter never formed); the
CheckQuorum window is the transport's request timeout plus an election
timeout for every job group too. Verified on real managers by the
in-process datacenter simulations (`tests/unit/simulation/sim/test_manager_*`):
three managers form their membership over the SIM transport, and a lone
manager restarted mid-job resumes it once its membership forms, with what
is left of its budget.

**Fencing (decided 2026-10, against section 6's per-RPC header).** A
cluster here is founded anew whenever the last one can no longer commit --
there is no storage to carry it through -- while job groups and job
leadership belong to processes, which a refounding leaves running. A
cluster-uuid check on every RPC would fence every running job at every
refounding. So each concern section 6 lists is enforced where it lives:
the membership group's own traffic is keyed by its cluster uuid
(`cluster:{uuid}`; another cluster's votes and entries are ignored) and its
formation and join messages by the cohort digest; a removed member's Raft
traffic is refused by its group's configuration and terms (CheckQuorum
deposes a stale leader); a stale job leader is fenced by AD-10 fence
tokens.

## Context

Hyperscale is a long-running control plane and job server, not a short-lived test runner. Gate clusters and per-DC manager clusters are expected to run for months or years, hosting the global job ledger (AD-38), idempotency state (AD-40), SLO digests (AD-42), retry budgets (AD-44), and learned route state (AD-45). Worker fleets are ephemeral; the control plane is not.

The cluster registry and join mechanism must:

1. Work in every reasonable deployment substrate — Kubernetes, bare VMs, Mesos, Nomad, ECS/Fargate, Cloud Run, Docker Swarm, bare metal, and dev laptops — with **one** protocol path, not per-environment branches.
2. Require zero persistent storage on any node (no PVCs, no local-disk dependencies for correctness).
3. Be internal to Hyperscale; no reliance on etcd, ZooKeeper, Consul, cloud provider APIs, K8s API server, multicast, broadcast, or NTP.
4. Match the correctness bar of state-of-the-art consensus databases (etcd, CockroachDB, Spanner) and the robustness bar of battle-tested service registries (Istio, Linkerd).

Complexity is not a goal but is not a constraint either; correctness, robustness, and performance dominate.

## Decision

A unified cluster formation and membership protocol with the following properties:

- **Deterministic bootstrap** via an explicit `--initial-members` list on the founding nodes; bootstrap and join are distinct protocols.
- **Raft-replicated membership** in each cluster's existing Raft group (gate cluster, per-DC manager cluster), with **joint consensus** (C_old,new) for atomic membership changes.
- **Learner state** for new joiners: non-voting catch-up via snapshot + log streaming, promoted to voter only when log lag is within threshold.
- **Membership-generation fencing** on every cluster RPC: `(cluster_uuid, membership_epoch, sender_node_id, sender_term)` validated by receivers.
- **Pluggable seed locators** (`tcp://`, `dns://`, `dns-srv://`, `file://`, `exec://`) so any environment can produce a seed list without Hyperscale depending on environment-specific APIs.
- **SWIM + phi-accrual hybrid** failure detection: SWIM gossip drives cluster-wide convergence (AD-27, AD-30); phi-accrual drives per-edge circuit-breaking decisions (extending AD-18).
- **Watch streams** for membership distribution: leader pushes deltas, like etcd watch / xDS, with reconnect-and-resync.
- **Disconnected mode** for the data plane: every node maintains a soft-state cache of the last-known cluster view; data plane keeps serving when control plane is unreachable.
- **Cluster UUID as generation marker**, minted at bootstrap and stored in Raft state (independent of mTLS cert lifecycle).
- **Ephemeral node identity**: `node_id = uuid4()` per process start; restarts are new joins, never rejoins.
- **Determinism boundary** at the state machine apply layer: log entries are the only input to state transitions.

## Non-goals

- Total catastrophic recovery (every region's gate cluster dying simultaneously). Unrecoverable without external durability; documented as such.
- Surviving total cluster-wide configuration loss without operator intervention. Bootstrap is operator-driven.
- Automatic horizontal scaling of the control plane (gates/managers). HPA-style scaling is for workers; control plane resize is operator-triggered via explicit `ResizeCluster` log entry.
- Multicast / broadcast discovery. Unsupported in most cloud environments.

## 1. The universal environment contract

The deployment substrate must provide exactly three things. Anything beyond this is a shortcut and is explicitly rejected.

1. **A way to launch a process with config** (env vars and/or flags). Every orchestrator supports this.
2. **TCP connectivity between nodes that can reach each other** at some address. No assumption about IPv4 vs IPv6, NAT, link-local, dual-stack, or specific port ranges.
3. **A way to provide each node with a seed locator string at launch.** This is the irreducible bootstrap input.

### Explicitly forbidden assumptions

The protocol must not depend on, and must continue to operate correctly without, any of:

- Stable IP addresses across process restart.
- Stable hostnames. Hostnames are opaque label hints, never identity.
- Persistent storage of any kind. No PVCs, no local files surviving restart. (A disk the node can verify as its own is used to resume -- D1 -- but correctness never depends on one.)
- Synchronized wall clocks (NTP not required). Ordering uses Hybrid Logical Clocks (AD-38). Wall clock is used only for observability, never for correctness.
- DNS being available, fast, or honest. If DNS fails, alternative locator types must work.
- Predictable orchestrator restart semantics. Hyperscale exits non-zero on unrecoverable error; whoever launched it decides what to do.
- Specific port numbers. Every address includes its port.
- Orchestrator-specific service discovery (K8s API, Mesos master, Consul, etc.). Hyperscale only resolves what the operator passes in `--seeds`.
- Cert lifecycle automation. mTLS material is read from configured paths; rotation policy is outside scope.
- `node_id` continuity across process restart. A restarted process is a new member, period.
- `cluster_size` knowability at join time. Founding members must agree on it at bootstrap; subsequent joiners learn it from Raft state.

## 2. Seed locator: the only environment-facing primitive

A seed locator is a URI-style string Hyperscale resolves internally. Five scheme handlers, all implemented inside Hyperscale:

| Scheme | Form | Resolution |
|---|---|---|
| `tcp://` | `tcp://10.0.5.7:8080` | Literal address. Port required. |
| `dns://` | `dns://manager.svc.cluster.local:8080` | OS-level name resolution (uses `/etc/hosts`, DNS, mDNS, NSS, whatever the OS provides). All A/AAAA records returned. |
| `dns-srv://` | `dns-srv://_hyperscale._tcp.svc` | DNS SRV record lookup. Service+port from the record. |
| `file://` | `file:///etc/hyperscale/seeds` | Read newline-delimited locators from a file. Watched via mtime, re-read on change. |
| `exec://` | `exec:///opt/get-seeds.sh` | Execute a command, parse stdout (one locator per line). Refreshed on a configurable interval (default 60s). |

`--seeds` accepts a comma-separated list of locators. Resolution semantics:

- Resolve all locators, dedupe address results.
- Re-resolve on a jittered interval (default 60s, jitter 0–20% per AD-21).
- Re-resolve on any connection failure to a previously resolved address.
- An empty resolution is not an error; the locator may produce results later.
- A locator returning 1000+ addresses is bounded by `--max-seed-candidates` (default 64); excess is sampled with weighted rendezvous hashing per AD-28.

### Environment mapping

| Environment | `--seeds` value |
|---|---|
| Kubernetes (headless Service) | `dns://manager-headless.ns.svc.cluster.local:8080` |
| Kubernetes (SRV-configured) | `dns-srv://_hyperscale._tcp.manager-headless.ns.svc` |
| Cloud VMs with cloud DNS | `dns-srv://_hyperscale._tcp.internal` |
| Cloud VMs raw | `tcp://10.0.1.5:8080,tcp://10.0.1.6:8080,tcp://10.0.1.7:8080` |
| Mesos with Mesos-DNS | `dns://hyperscale.marathon.mesos:8080` |
| Nomad | `dns://hyperscale.service.consul:8080` or `exec:///opt/nomad-seeds.sh` |
| ECS / Fargate (Cloud Map) | `dns://hyperscale.local:8080` |
| Docker Swarm | `dns://tasks.hyperscale:8080` |
| Bare metal | `file:///etc/hyperscale/seeds` |
| Dev laptop | `tcp://127.0.0.1:8081,tcp://127.0.0.1:8082,tcp://127.0.0.1:8083` |
| Air-gapped / edge | `file:///etc/hyperscale/seeds` |
| Spot/preemptible | identical to the steady-state environment |

Hyperscale's code paths are identical across all of these. Only the locator string differs.

### Security note on `exec://` and `file://`

Both schemes accept input from outside the process. The configuration paths are operator-controlled (env vars, flags); they must not be sourced from network input. The runtime enforces:

- `exec://` paths must be absolute and on a filesystem owned by the process user, with no world-writable parent directories. Otherwise it's a refused locator with a loud log line.
- `file://` paths are read with the same ownership/permission checks.
- Locator strings are never logged with full path; only the scheme is logged at INFO, full path at TRACE.

## 3. Cluster identity

Every node carries five identity fields at startup. These are the irreducible configuration.

| Field | Source | Purpose |
|---|---|---|
| `cluster_id` | `--cluster-id` | Human-readable identifier (e.g., `prod-uswest-managers`). Admission check at handshake. |
| `role` | `--role` | One of `gate`, `manager`, `worker`. Enforced against mTLS cert subject. |
| `mTLS material` | configured paths | Cert chain + key, validated against a cluster CA. Cert subject must declare the matching role per AD-28 connection matrix. |
| `node_id` | generated | `uuid4()` at process start. Never persisted, never reused, never inferred. |
| `advertised_address` | `--advertised-address` (optional) | Address peers should use to reach this node. If unset, derived from the source IP of the first successful peer handshake. |

`cluster_uuid` is **not** node configuration. It is minted at bootstrap, committed as the first Raft entry, immutable thereafter, and learned by joiners from the leader during handshake. It is the cluster-generation marker (Section 6).

### Why `node_id` is ephemeral

Three reasons:

1. **No assumed substrate has stable identity that survives all restart conditions.** K8s pod hostnames are unstable on Deployment-style workloads; cloud VM hostnames can be changed by image regeneration; bare-metal machines can be reimaged.
2. **Stable identity is an optimization, not a correctness requirement.** A restarted process being a "new member" costs two Raft log entries (REMOVE old, ADD new). This is negligible at control-plane restart rates.
3. **Simplifying the model eliminates an entire class of bugs.** No "rejoin" path means no node-identity hijacking, no incarnation-number races, no two-pods-claiming-the-same-identity edge cases.

The cost is faster eviction-then-readmission on pod restart; Raft handles this trivially.

## 4. Bootstrap protocol (cold formation)

Bootstrap is a separate operation from join. A node bootstraps only when:

- It is launched with `--initial-members=<list>` and the list includes its own `node_id`, AND
- It can successfully reach a quorum of the other initial members and confirm they are also bootstrapping the same cluster.

Otherwise, the node joins an existing cluster via Section 5.

### Why `--initial-members` is required

In my earlier drafts of this design I proposed "lowest node_id over a discovery window runs pre-vote." That approach has the following race: if seed resolution returns different views to different candidates during the bootstrap window (DNS propagation lag, partial visibility, etc.), two candidates can independently conclude they are the bootstrap leader and propose competing initial membership logs. While Raft pre-vote (AD-5) would eventually reject one, the race window admits operator confusion and observable cluster-split symptoms.

The state-of-the-art (etcd `--initial-cluster`, ZooKeeper `myid`) makes bootstrap deterministic by requiring operators to enumerate the founding members. Hyperscale follows this pattern.

### `--initial-members` format

```
--initial-members=node_id_1@locator_1,node_id_2@locator_2,node_id_3@locator_3
```

Each entry binds a `node_id` to an address locator. The list is:

- Identical on every founding node (mismatches abort bootstrap with a loud error).
- Sized exactly `cluster_size` (mismatches abort bootstrap).
- Ignored after the first commit of the seed membership log entry; subsequent restarts of these same nodes proceed as normal joins.

The `node_id` fields here are *operator-assigned founding identifiers*, not the `uuid4()` runtime IDs. They serve only to map founding-member-slots to addresses at bootstrap time. After commit, the membership is keyed on the runtime `uuid4()` IDs of the founding processes.

### Bootstrap state machine

```
                            no --initial-members
                          ┌─────────────────────────────────────┐
                          │                                     │
                          ▼                                     │
                  ┌──────────────┐                              │
                  │  DISCOVERING │  resolve seeds, probe peers  │
                  └──────┬───────┘                              │
                         │                                      │
              any peer JOINED                                   │
                         │                                      │
                         ▼                                      ▼
                  ┌──────────────┐                       ┌─────────────┐
                  │  JOINING     │ ─────────────────────►│   JOINED    │
                  └──────────────┘  ADD committed via    └─────────────┘
                                    leader                       ▲
                                                                 │
                          --initial-members on launch            │
                                  │                              │
                                  ▼                              │
                          ┌──────────────┐                       │
                          │  FORMING     │ confirm peers, run    │
                          └──────┬───────┘ pre-vote at term 1   │
                                 │                               │
                            quorum confirmed                     │
                                 │                               │
                                 ▼                               │
                          ┌──────────────┐                       │
                          │ BOOTSTRAPPING│ propose seed log,    │
                          └──────┬───────┘ commit to majority   │
                                 │                               │
                                 └───────────────────────────────┘
```

### Bootstrap algorithm

1. Each founding node loads `--initial-members`, validates its own `node_id` is in the list, validates list size equals `cluster_size`.
2. Each founding node resolves the locators of the other initial members and TCP+mTLS handshakes them.
3. Handshake exchange: `BootstrapHello { my_node_id, cluster_id, role, initial_members_hash, runtime_uuid }`. The `initial_members_hash` is `sha256(sorted(initial_members))`. Receivers reject the handshake if their own hash differs.
4. Once a node has received valid `BootstrapHello` from a quorum of the initial set, it runs Raft pre-vote (AD-5) at term 1.
5. Pre-vote winner proposes the seed membership log entry: `EnterJoint { old_members: ∅, new_members: <runtime_uuids of founding set> }` at term 1.
6. On commit at majority, the winner proposes `LeaveJoint { members: <runtime_uuids> }`, completing the joint-consensus transition.
7. Same Raft transaction commits the `cluster_uuid` (newly minted `uuid4()`) and `cluster_size` as cluster state.
8. Bootstrap complete. The cluster is in `JOINED` state.

If any of the above fails (pre-vote timeout, conflicting `initial_members_hash`, unreachable quorum), the node exits non-zero with a structured error. The operator's process supervisor (or the operator) handles retry.

## 5. Join protocol (existing cluster)

A node without `--initial-members` (or whose initial-members list is rejected because the cluster has already formed) joins an existing cluster.

### Join algorithm

1. Node loads identity, generates `node_id = uuid4()`, resolves seeds.
2. For each candidate address, TCP+mTLS handshake. mTLS cert chain validated against cluster CA; cert subject role must match `--role` per AD-28 matrix.
3. Send `JoinHello { node_id, cluster_id, role, protocol_version, capabilities, advertised_address_hint }`.
4. Receive `HelloResponse { their_node_id, their_role, cluster_uuid, cluster_state, leader_hint, membership_epoch, current_membership_size, server_capabilities }`.
5. Validate:
   - `their.cluster_id == my.cluster_id` (else: wrong cluster, refuse).
   - `protocol_version` major matches (AD-25, else: refuse).
   - `their_role` is in the AD-28 allowed-source-role set for my role.
6. If `cluster_state == JOINED`, follow `leader_hint`. If the responder is the leader, proceed in-place. Otherwise open a connection to the leader.
7. Send `JoinRequest { node_id, role, advertised_address, capabilities, attestation }` to the leader.
8. Leader validates and proposes `AddLearner { node_id, role, advertised_address, capabilities, learner_added_at_epoch }` via Raft.
9. On commit, leader replies `JoinAccepted { cluster_uuid, current_membership, current_membership_epoch, cluster_size, fence_token }`.
10. Joining node enters **learner** state (Section 7), begins receiving snapshot + log via Raft InstallSnapshot + AppendEntries.
11. When learner's commit index is within `learner_promote_threshold` (default 256 entries) of leader, leader proposes `Promote { node_id }`.
12. On commit, joiner becomes a voting member. State transitions to `JOINED`.

### Advertised address resolution

The node's `advertised_address` (what peers use to reach it) is determined by:

1. If `--advertised-address` is set, use it (subject to reverse-probe verification in environments where peers can't trust client-asserted addresses).
2. Otherwise, accept the source IP of the incoming TLS connection during the leader handshake as the advertised address. This is the SOTA-default ("source-of-truth is what worked"), and avoids the failure modes of reverse-probing through asymmetric firewalls.
3. Reverse-probing is opt-in via `--verify-advertised-address` for environments where source-IP can be spoofed (rare in mTLS environments since the cert binds identity, but available for defense-in-depth).

Address changes mid-life (e.g., K8s pod recreation on a new host) are handled by full re-join with a new `node_id`, not by an in-place update. The old `node_id` is evicted via Section 8.

## 6. Membership log and joint consensus

The cluster's membership state is replicated via the cluster's existing Raft group:

- Gate cluster: global Raft (members spread across regions).
- Per-DC manager cluster: regional Raft (members within one DC).

Workers are not in any Raft group; their registration is handled in Section 12.

### Membership log entry types

All entries are versioned (Section 14) and include `(committed_at_term, committed_at_epoch)` metadata.

| Entry | Fields | Purpose |
|---|---|---|
| `EnterJoint` | `old_members`, `new_members`, `cluster_uuid_at_create` | Begin joint-consensus transition. Quorum requires majorities of *both* configurations. |
| `LeaveJoint` | `members` | Complete joint transition. Quorum now requires majority of new only. |
| `AddLearner` | `node_id`, `role`, `advertised_address`, `capabilities` | Add non-voting member receiving log replication. |
| `Promote` | `node_id` | Promote learner to voter. May trigger an `EnterJoint`/`LeaveJoint` pair if it changes the voting set. |
| `Remove` | `node_id`, `reason ∈ {leave, evict, force}` | Remove a member. Triggers `EnterJoint`/`LeaveJoint`. |
| `UpdateMetadata` | `node_id`, `metadata_delta` | Update non-identity metadata (capabilities, role-aware bracket settings, drain status). |
| `ResizeCluster` | `new_cluster_size` | Operator-driven resize. Forces joint-consensus path. |

### Why joint consensus

Single-server membership changes are correct in the original Raft paper but only under the assumption that the cluster cannot suffer a partition during the change. In practice, single-step changes admit failure modes where a minority partition believes it has the new quorum:

- Cluster of 3 (A, B, C). Operator removes C. During the change, a partition isolates {A, B} from {C}.
- {A, B} thinks the new config is {A, B} (2-node majority is 2). It elects a leader and writes.
- {C} thinks the old config is {A, B, C}. It cannot make progress because it can't reach a majority.
- This is safe in this example, but a subsequent change while C is partitioned can transition into a configuration where C's stale view conflicts.

Joint consensus eliminates this entire class. During `EnterJoint`/`LeaveJoint`, any commit requires majorities of *both* configurations. Minority partitions cannot complete the transition because they lack one of the required majorities.

### Membership-generation fencing

Every cluster RPC carries a fence header:

```
ClusterRPCFence {
    cluster_uuid:          uuid              # bootstrap-minted, immutable
    membership_epoch:      u64               # incremented per committed membership change
    sender_node_id:        uuid              # runtime id of sender
    sender_term:           u64               # current Raft term as known by sender
    sender_membership_lsn: u64               # last membership entry sender has applied
}
```

Receivers validate:

| Check | Rejection reason |
|---|---|
| `fence.cluster_uuid != receiver.cluster_uuid` | `WRONG_CLUSTER` — zombie from destroyed cluster |
| `fence.sender_node_id ∉ receiver.current_membership` | `STALE_MEMBER` — sender was removed |
| `fence.sender_term < receiver.current_term` | `STALE_TERM` — sender is from an old leadership epoch (AD-10) |
| `fence.membership_epoch < receiver.membership_epoch - max_membership_lag` | `STALE_MEMBERSHIP` — sender's view is too far behind |

The fence is checked at the protocol layer before any handler runs. Rejected RPCs return a structured `ClusterFenceError` so the sender can self-correct (resync membership, refresh `cluster_uuid`, exit if zombie).

This is the AD-10 fence-tokens-from-terms idea extended along the membership axis. Together they eliminate the "stale node writing into the wrong cluster" failure mode.

## 7. Learner state and safe catch-up

When a new member is added via `AddLearner`, it does not vote and does not count toward quorum. The cluster size from a quorum-calculation perspective is unchanged.

### Learner lifecycle

```
                  AddLearner committed
                          │
                          ▼
                   ┌──────────────┐
                   │   LEARNER    │  receive snapshot + log
                   └──────┬───────┘
                          │
              commit_index within
              learner_promote_threshold
              of leader's commit_index
                          │
                          ▼
                   ┌──────────────┐
                   │  PROMOTING   │  leader proposes Promote
                   └──────┬───────┘
                          │
                  Promote committed
                  (joint-consensus
                   transition if voting
                   set changes)
                          │
                          ▼
                   ┌──────────────┐
                   │    VOTER     │  full member
                   └──────────────┘
```

### Why learners

A new joiner can lag the leader by gigabytes of state machine. If it became a voter immediately:

- It could be the deciding vote in an election but unable to actually replicate (would hold up commits).
- It could win an election (if it had a higher term) and roll back committed entries it never received.
- It could artificially expand the quorum size before having state, transiently making it harder to reach quorum.

Learner state is the SOTA solution: catch up first, promote later, vote never as a learner.

### Promotion threshold

`learner_promote_threshold` is the maximum log lag (in entries) at which a learner can be promoted. Default 256 entries; configurable per-cluster. Tuning:

- Lower threshold → promotion happens sooner after catch-up, faster cluster scale-up.
- Higher threshold → less risk of immediate slow follower, more headroom for replication transient slowdowns.

If a learner cannot catch up within `learner_max_lifetime` (default 30 minutes), the leader proposes `Remove { node_id, reason: evict }` — the joiner is too slow and is rejected. The operator's substrate restarts the process, generating a new `node_id`, and it tries again.

## 8. Failure detection: SWIM + phi-accrual hybrid

Two complementary detectors, both running:

### SWIM gossip (cluster-wide convergence)

Existing implementation (AD-27, AD-29, AD-30, AD-35, AD-46). Drives the cluster-wide view of who is alive, suspect, dead. SWIM events feed the **eventual** REMOVE proposal but never directly cause REMOVE — that path is Raft only.

SWIM transitions for an existing voter:

```
ALIVE ──Lifeguard suspicion bracket──► SUSPECT
SUSPECT ──multiple indirect probe failures──► DEAD
DEAD ──tombstone_retention (default 10min)──► REMOVE proposed via Raft
```

The 10-minute tombstone retention is deliberate. Transient network partitions are the common case; actual node death is the rare case. Service registries that evict aggressively (e.g., DNS TTLs of seconds) cause real production outages on every network blip. The SOTA bar (Linkerd, Istio) holds endpoints for minutes after they look dead, because real death is rare and brief blips are common.

### Phi-accrual (per-edge probabilistic detection)

Phi-accrual (Hayashibara et al., used in Cassandra, Akka, Hazelcast) computes a continuously-updated suspicion value φ per peer-to-peer edge:

```
φ(t) = -log10(P(heartbeat arrives by t | history))
```

Higher φ = higher confidence the peer is unreachable from *this* node. Threshold typically 8.0 for declaring failure; warning at 4.0.

Phi-accrual feeds:

- **Connection circuit breakers** (extending AD-18). High φ for a peer trips its circuit breaker; subsequent requests fail fast.
- **Per-edge routing decisions**. If φ to manager M from gate G is high, G routes jobs elsewhere even if M is still cluster-ALIVE from other gates' perspectives. This is the locality-aware piece of AD-36 hardening.
- **SWIM probe budgeting**. Edges with high φ get more frequent probes; healthy edges get fewer.

Phi-accrual uses AD-35 Vivaldi RTT estimates as the baseline expected inter-arrival time, so the detector adapts to network topology. Cross-DC edges naturally have higher baselines than intra-DC edges.

### Multi-stage eviction summary

```
Stage             Timer (default)         Trigger
─────────────────────────────────────────────────────────────────
ALIVE → SUSPECT    Lifeguard bracket       SWIM probe miss
SUSPECT → DEAD     ~10s                    indirect probe failures
DEAD → tombstone   instant                 cluster gossip convergence
Tombstone → Remove 10 min                  Raft REMOVE proposed by leader
```

The four-stage progression means a peer must be unreachable from the leader's perspective for ~10 minutes before being removed from membership. This is the "battle-tested" tolerance for blips.

Operator escape: `force-remove` (Section 13) skips the tombstone and proposes REMOVE immediately. Required for situations where the operator knows the node is gone (e.g., physical hardware destroyed) and wants the cluster to reform faster.

## 9. Watch streams for membership distribution

Every node opens a long-lived **watch stream** to the cluster (initially to a follower for load distribution; failover to leader for higher consistency). Watches replace polling.

### Watch protocol

```
WatchOpen {
    last_seen_membership_epoch: u64
    last_seen_lsn:              u64
    watch_filter:               { entry_types, node_id_subset }
    watcher_node_id:            uuid
}
```

Server response:

```
WatchSnapshot {
    snapshot_epoch:      u64
    snapshot_lsn:        u64
    membership_at_lsn:   list[MemberRecord]
    cluster_uuid:        uuid
    cluster_size:        u32
}
```

Then a stream of:

```
WatchDelta {
    epoch:       u64
    lsn:         u64
    entry:       MembershipLogEntry
    apply_after: lsn
}
```

### Reconnect semantics

On disconnect, client reconnects with `last_seen_lsn`. Server responds with either:

- `WatchDelta` stream from `last_seen_lsn + 1` if the LSN is within snapshot retention.
- A fresh `WatchSnapshot` if the LSN has rolled past retention (catastrophic disconnect).

The server maintains a bounded ring buffer of recent log entries (default 16384, configurable) to serve reconnects. Beyond that, clients re-snapshot.

### Why watches, not polls

Polling has p99 latency proportional to poll interval and load proportional to cluster size × poll rate × node count. Streams scale with churn rate, which is orders of magnitude lower in steady state.

This is the etcd watch / Envoy xDS / Linkerd Destination API pattern. It is the SOTA bar for control plane distribution.

## 10. Disconnected mode for the data plane

The control plane (cluster membership Raft) and the data plane (job execution) are separated by a soft-state cache. The data plane never blocks on the control plane.

### Soft-state cache

A node that follows a cluster it is not a member of -- a gate following each datacenter's managers, a worker following its own datacenter's -- holds the membership it last observed in a `ClusterViewCache` (`hyperscale/distributed/cluster/cluster_view_cache.py`), fed by a `ClusterWatchFollower` long-polling the watch (Section 9):

```
ClusterViewCache {
    view:        ClusterView { cluster_uuid, applied_index, holders, cohort, voters, learners, mode }
    observed_at: monotonic seconds -- when the poll that brought the view was SENT
}
```

The view is dated by when its poll was sent: the member answered after that, so the view is at least that fresh.

### Staleness accounting

`read(now)` returns `(view, staleness_seconds = now - observed_at)` -- infinite before the first observation. Consumers choose:

- **Linearizable required**: ReadIndex against the membership group (Section 11), one round trip.
- **Bounded staleness**: re-read once the staleness passes the bound.
- **Best-effort**: take the view as it is.

The consumers today, all best-effort:

- A gate's per-datacenter view becomes the managers it routes to there (`GateServer._reconcile_datacenter_managers`): the cohort's arrivals are registered with, its departures forgotten.
- A worker's view of its datacenter becomes its rejoin seeds (`WorkerClusterConnection.adopt_cohort`).

### Disconnected mode

A healthy watch's view is never staler than two polls: the poll that brought it took up to its wait plus its request budget to answer, and the next -- sent at once -- as long again. A staleness past `2 * (CLUSTER_WATCH_WAIT_SECONDS + request timeout)` therefore proves the watch cannot reach the cluster: the cache counts **disconnected** (`is_disconnected(now)`). The bound is derived from the watch's own timings, not configured.

While disconnected:

- The view is still served, its staleness growing; routing and rejoin keep using the last cohort.
- Workers keep executing in-flight workflows (AD-4: workers are the source of truth for them) -- nothing on the execution path reads the membership view.
- Managers keep accepting dispatches; AD-38 durability is unaffected (the job ledger is not the membership group).
- Gates keep routing to the managers last observed; AD-36 health still comes from manager heartbeats, not from the view.

Each entry into and exit from disconnected mode is reported once, as it happens (the follower's `on_disconnected_changed`), and logged by the gate (per datacenter) and the worker as `ClusterWatchConnectivityChanged` -- WARN entering, INFO leaving, with the staleness at that moment. A gate's `hyperscale cluster --metrics` exports, per datacenter, `cluster_watch_staleness_seconds` (`+Inf` before the first observation), `cluster_watch_disconnected` and `cluster_watch_applied_index`.

When the watch reaches the cluster again, its first answer refreshes the view (a snapshot if the cluster moved past what it can replay) and the consumers reconcile against it.

### Datacenter regeneration

A datacenter whose managers all lost their data founds a new cluster under the same datacenter id (Section 17): its watch answers with a different `cluster_uuid`. The gate remembers the cluster each datacenter last answered as; a view of a different one forgets what it learned of the old incarnation -- its AD-45 observed latency and any AD-42 SLO violation it was timing -- once, logged as `DatacenterRegenerated`. Manager health and capacity are per manager address and refresh from the new managers' heartbeats.

### Scope of the guarantee

Control plane outage is not a data plane outage (the Linkerd / Istio pattern): with the membership group unreachable, nothing on the dispatch or execution path waits on it, so jobs keep running; what degrades is the freshness of the manager lists gates route to and workers rejoin from, which a membership change made during the outage cannot reach until the watch reconnects.

## 11. Linearizable reads via ReadIndex

For any read that must be linearizable (e.g., "what is the current cluster membership at this exact moment?"), use the Raft ReadIndex protocol:

1. Reader (any voter) asks the leader for the current commit index.
2. Leader verifies it is still leader by exchanging heartbeats with a quorum (or relies on its current leader lease, see below).
3. Leader replies `(commit_index_at_read)`.
4. Reader waits until its local apply index reaches `commit_index_at_read`.
5. Reader serves the read from its local state machine.

No log entry is written for reads. Cost: one round-trip from reader to leader, plus the leader's quorum verification (which is batched across many concurrent reads).

### Leader leases

The leader optionally holds a lease for `quorum_timeout / 2`. While the lease is valid, the leader can answer ReadIndex requests without quorum verification (because it knows no other leader has been elected). On lease expiry, full quorum verification is required.

Leases require bounded clock skew, which Hyperscale does not assume in general. Therefore leases are opt-in via `--leader-lease-enabled` and require operator opt-in to bounded-skew (NTP available). When disabled (the default), full quorum verification is always performed; this costs one round-trip per ReadIndex but requires no clock-skew assumption.

### Stale reads from followers

Followers can serve reads with bounded staleness without contacting the leader. The follower's apply index is "behind by some amount" relative to the leader; the staleness bound depends on replication lag. AppendEntries throughput is the limiting factor; in steady state, lag is sub-millisecond.

## 12. Workers (not in Raft)

Workers do not form a cluster. They are ephemeral, high-churn, and explicitly exempted from consensus participation (AD-38). Each worker has a single owner manager; AD-48 disseminates worker state across managers within a DC.

### Worker join

1. Worker starts, generates `node_id = uuid4()`.
2. Resolves `--manager-seeds` (same locator system as Section 2).
3. Probes candidate managers using AD-28 weighted rendezvous + power-of-two-choices for load balancing.
4. Selected manager: TCP+mTLS handshake, exchange `WorkerHello { node_id, capabilities, advertised_address }`.
5. Manager validates (cluster_id, role per AD-28 matrix), accepts via *local* registration (no Raft entry).
6. Manager broadcasts `WorkerStateUpdate { node_id, owner_manager, state: REGISTERED, incarnation }` to peer managers via AD-48.
7. Worker is now functional.

### Why workers skip Raft

Worker fleets are 10-1000x larger than control plane clusters and churn 100-1000x more frequently (HPA scaling, per-test fleets, spot preemptions). Putting workers in Raft would:

- Bloat the membership log with high-frequency churn.
- Slow Raft apply by orders of magnitude.
- Make the control plane susceptible to worker-fleet incidents.

Instead, worker registration is **local to the owner manager** (in-memory + AD-38 LOCAL tier WAL for crash recovery within a pod) and **propagated** via AD-48 (TCP broadcast for critical events, gossip piggyback for steady state). This is the architectural separation called out in AD-38 ("workers never participate in consensus").

### Worker failure handling

- Worker SWIM-dies → owner manager detects via heartbeat timeout.
- Owner manager broadcasts `WorkerStateUpdate { state: DEAD }` to peer managers (AD-48).
- Workflows on that worker are reassigned via AD-4 / AD-31 leadership protocols.
- No Raft REMOVE is needed because there's no Raft entry to remove.

### Worker manager failover

If a worker's owner manager dies, the worker detects via SWIM (AD-7), drops the registration, and re-registers with another manager. AD-31 ensures job leadership for affected workflows transfers correctly.

## 13. Operational primitives

### Drain

```
POST /admin/drain
  → Node marks itself draining (UpdateMetadata Raft entry).
  → Leader stops routing new work (job dispatch, worker assignments) to this node.
  → In-flight work continues until completion.
  → Node sends LeaveRequest when drained.
```

### Force-remove

Operator escape for unresponsive members, gated by epoch:

```
POST /admin/force-remove?node_id=<id>&current_epoch=<epoch>
  → Leader validates current_epoch matches its membership_epoch.
  → Leader proposes Remove { node_id, reason: force } via Raft.
  → Skips tombstone retention; immediate removal on commit.
```

The `current_epoch` parameter is required and validated; this prevents the "operator removed the wrong node after the cluster churned" failure mode. If the epoch is stale, the request is rejected with the current epoch in the error, and the operator can retry.

### Membership freeze

```
POST /admin/freeze
  → Leader sets a freeze flag (UpdateClusterMetadata Raft entry).
  → All membership change proposals (AddLearner, Promote, Remove) are rejected with FROZEN error.
  → Useful during maintenance windows or while debugging.

POST /admin/unfreeze
  → Clears the flag.
```

### Snapshot export/import

```
POST /admin/snapshot/export
  → Returns a tarball: { cluster_uuid, membership_epoch, raft_state, soft_state }.
  → Used for disaster recovery and audit.

POST /admin/snapshot/import (only on a freshly-launched cluster)
  → Validates the cluster has no committed state.
  → Imports the snapshot; mints a NEW cluster_uuid (prevents accidental fork).
  → Logs a structured event noting the import source.
```

Import always mints a new `cluster_uuid` so an imported cluster cannot be confused with the original. This prevents the "I restored a snapshot and now have two clusters with the same identity" failure mode.

### Read-only mode

```
POST /admin/read-only
  → Cluster refuses all writes (membership changes, job submissions, etc.).
  → Reads continue.
  → Used during upgrades and dangerous maintenance.
```

## 14. Schema versioning

Every Raft log entry carries a schema version prefix:

```
LogEntry {
    schema_version: u32
    entry_type:     u32
    payload:        bytes (versioned encoding)
}
```

The apply layer dispatches on `(entry_type, schema_version)`. Old schemas remain supported until a configurable retention (default: two major releases). Forward compatibility (unknown fields ignored) is per AD-25.

### Schema migration

When a new field is added to an entry type:

1. Define schema version `N+1` that includes the new field.
2. Apply layer supports both `N` and `N+1` simultaneously.
3. Writers emit `N+1`.
4. After all nodes are on the new version (negotiated via AD-25 capabilities), writers may continue emitting `N+1`.
5. After retention window, support for `N` can be removed.

This is the standard SOTA approach (etcd v3 schema, CockroachDB versioned migrations). Hyperscale piggybacks on AD-25's protocol versioning for transport-level compat and adds explicit Raft-log schema versioning for state-machine compat.

## 15. Determinism boundary

The Raft state machine **apply layer** is a hard determinism boundary. Violations cause divergence between followers (different state machines from the same log = catastrophic).

### Determinism rules (enforced at apply layer)

- **No wall clock.** `time.time()`, `time.time_ns()`, `datetime.now()` are forbidden in apply code. Time-like inputs come from HLC timestamps embedded in log entries (AD-38).
- **No randomness.** `random.random()`, `os.urandom()` are forbidden. If randomness is needed, the seed must be in the log entry.
- **Sorted iteration over maps and sets.** Python's `dict.items()` ordering is insertion-order but iteration over `set` is not stable across Python versions or platforms. Apply code uses `sorted(d.items())` and `sorted(s)`.
- **No filesystem reads.** Apply layer has no I/O.
- **No network calls.** Apply layer has no I/O.
- **No hash-based identity.** Hashes of objects, addresses, etc. are non-deterministic across runs. Use explicit IDs.

These rules are enforced by:

- **Static lint rule** (custom Ruff plugin) that flags forbidden imports/calls in `cluster/state_machine_apply.py` and related modules.
- **Runtime assertion** in test mode that runs apply with two random seeds and compares output (chaos test catches non-determinism).
- **Code review checklist** for any change to apply code.

This is the Jepsen-clean bar. Without it, Raft followers will silently diverge on rare inputs and the cluster will be quietly broken.

## 16. Throughput primitives

### Group commit on the Raft WAL

Following AD-38's NodeWAL pattern, the Raft log writer:

- Collects pending log entries from concurrent proposals.
- Batches into a single `write() + fsync()` call.
- Resolves all proposers' futures after fsync completes.

Throughput: at 500μs fsync latency, ~2000 batches/sec × 100-1000 entries per batch = 200K-2M entries/sec.

### AppendEntries batching, not pipelining

The leader keeps one exchange in flight per follower and folds everything proposed meanwhile into the next one: `RaftPeerOutbox` runs one sender per peer, and an undelivered AppendEntries for a group is superseded by a newer one, which Raft rebuilds from current state and which carries every entry the follower still lacks. A slow follower delays only its own deliveries; memory is bounded by peers x groups x 2.

A per-follower in-flight window (sending AppendEntries(N+1) before N is acknowledged) is not built, because nothing would fill it:

- Every per-job group's proposals come from the job ledger, and `JobLedger` commits a job's entries one at a time, in append order (`JobCommitSequencer`). The next entry is proposed only after the last one committed (pinned by `test_ledger_commit_ordering.py::test_a_jobs_entries_replicate_in_append_order`). A group never has a second proposal to overlap with the first. Concurrency across jobs is concurrency across groups, which the per-peer outbox already overlaps.
- The membership group's proposals are claims, releases, mode changes and resizes: operator-rate, with no overlap to hide.

A window would add optimistic `next_index` bookkeeping and out-of-order reply handling for no measurable gain. If a workload ever proposes concurrently into one group, measure the commit latency against one round trip first; the window belongs in `RaftNode._send_append_entries_to`.

### Snapshot streaming

When a follower (or learner) falls too far behind, the leader sends a snapshot via `InstallSnapshot` instead of replaying the log. The snapshot is chunked and streamed; the receiver applies it directly to the state machine, skipping the log.

Snapshots are taken periodically (every `snapshot_interval_entries` log entries, default 10000) on each member independently. Snapshots are local (not gossiped) and used only for self-recovery and learner catch-up.

### Read concurrency

Reads via ReadIndex (Section 11) do not write the log and do not block writes. Read throughput is decoupled from write throughput. A read-heavy workload scales by adding followers.

### Performance targets

| Metric | SLO | Mechanism |
|---|---|---|
| Membership change commit (steady state) | p50 < 5ms, p99 < 50ms | One round trip to a quorum; concurrent proposals batch into the next exchange |
| Membership change commit (cross-region) | p50 < 100ms, p99 < 300ms | One cross-region round trip to a quorum |
| ReadIndex read | p50 < 2ms (intra-DC), p99 < 10ms | Lease (if enabled) or batched verification |
| Watch delta propagation | p50 < 5ms, p99 < 50ms after commit | Server-side dispatch on apply |
| Cold-cluster bootstrap | p99 < 10s | DNS resolution + 1 Raft round-trip |
| New-member join + learner-promote | p99 < 30s for 100MB state | Snapshot streaming |
| Failure detection (intra-DC) | < 5s to SUSPECT, < 15s to DEAD | SWIM + phi-accrual |
| Failure detection (cross-DC) | < 15s to SUSPECT, < 45s to DEAD | AD-35 role-aware brackets |
| Membership eviction (tombstone) | 10 min default | Configurable; tradeoff between blip tolerance and stale routing |

## 17. Multi-DC federation

The control plane is hierarchical:

- **Global gate cluster**: one Raft group, members spread across regions (e.g., 5 gates across 3 DCs). Its membership group holds the gates' membership; the gates replicate the global job ledger (AD-38) and idempotency decisions (AD-40) among themselves. Each gate learns datacenters for itself (below).
- **Per-DC manager cluster**: one Raft group per DC (typically 3-5 managers). Hosts local workflow state, AD-31 job leadership, AD-48 worker state propagation.
- **Workers**: not a cluster (Section 12). Registered with one owner manager per worker.

### How gates learn datacenters

There is no replicated datacenter catalog: each gate learns the datacenters it routes to from the datacenters themselves, so a datacenter is routable from a gate the moment that gate can reach its managers -- no gate-cluster commit stands between a datacenter coming up and jobs reaching it.

- **Configured**: the gate's datacenter manager addresses (`--datacenter-managers`), declared at start.
- **Joined**: `hyperscale join` names one manager; the gate registers with it, learns every healthy manager it reports for its datacenter, registers with each, and records the joined managers in its data directory (`JoinedPeerStore`) so a restart restores them.
- **Watched**: from then on the gate follows the datacenter's manager membership through a watch (Sections 9-10): the cohort the managers commit becomes the managers the gate routes to there.

Every gate does this independently; gates agree on jobs (AD-38's replicated ledger), not on the datacenter list. A datacenter one gate cannot reach is simply not a candidate at that gate -- AD-36 routing works from what each gate observes.

### DC regeneration

When a DC's manager cluster suffers catastrophic quorum loss and is founded again, the new cluster has a new `cluster_uuid`, which its watch replies carry. The gate remembers the cluster each datacenter's managers last answered as; on a different one it:

- forgets the datacenter's AD-45 observed latency and any AD-42 SLO violation it was timing -- learned of the old incarnation, they say nothing of the new one;
- logs `DatacenterRegenerated` (previous and new `cluster_uuid`), so the transition is observable;
- keeps per-manager health, capacity and Vivaldi coordinates, which are keyed by manager address and refresh from the new managers' heartbeats.

Jobs the old incarnation held are not fenced by a registration epoch: AD-38's job ledger and per-job fence tokens (AD-10) decide their ownership, and the gate's AD-31 orphan handling reclaims a job whose datacenter stopped answering for it.

### Bootstrap order

1. Gate cluster forms first (using `--initial-members` per Section 4).
2. Per-DC manager clusters form (each using its own `--initial-members`).
3. Each gate learns its datacenters by configuration or `hyperscale join`, then follows each one's membership by watch.
4. Workers join their owner manager (Section 12).

A manager cluster never waits for gates: clients may run jobs directly against one datacenter's managers, and gates that come up later register with the managers they learn. Workers wait only for their own managers; AD-21 jitter prevents thundering herds when managers return.

## 23. Open questions

The following are deliberate non-decisions, flagged for future resolution:

1. **`--initial-members` operator UX.** The list must be identical across founding nodes. Options: (a) operator types it on every node (error-prone but explicit), (b) Hyperscale provides a CLI tool that generates the list from a seed-list-at-bootstrap-time (operator runs once, copies output), (c) auto-generated and stored in a shared config object (defeats the "no external coordination" principle if taken too far). Leaning toward (b) — a tool, not magic.

2. **Leader lease semantics.** Enabled-by-default requires bounded clock skew; disabled-by-default costs one round-trip per ReadIndex. Cost is acceptable for control plane reads (few QPS); enabled-by-default may matter for very high-frequency data-plane reads. Leaning toward disabled-by-default with explicit operator opt-in.

3. **Snapshot import policy.** Should snapshot import require the new cluster to be freshly bootstrapped with the same `cluster_id` as the snapshot's source? Or should it always mint a new `cluster_uuid` regardless? The latter is safer (cannot accidentally fork); the former enables operators to "restore in place." Leaning toward latter.

4. ~~**DCRegistration history depth.**~~ Resolved: no replicated registration exists (Section 17); a regeneration is logged (`DatacenterRegenerated`) rather than retained as history.

5. **Phi-accrual threshold per role.** Phi=8 is the Cassandra default. Roles may benefit from different thresholds: workers under extreme load may need higher (slower to declare failure); cross-DC gates may need lower (faster to circuit-break). Probably defer until real load data is available.

6. **Watch fan-out at scale.** A 1000-worker cluster with each worker watching the manager-cluster generates 1000 watch streams. Followers can serve watches to distribute load, but this needs measurement. Mitigation if needed: hierarchical watch proxying (gates serve watches to their workers' managers, managers serve to their workers).

## Summary

AD-52 specifies a single cluster formation and membership protocol that runs on every reasonable deployment substrate, requires zero persistent storage, and meets state-of-the-art consensus-database and service-registry standards. The protocol is built on Hyperscale's existing primitives (Raft, SWIM, AD-28 discovery, AD-38 ledger, AD-46 IncarnationTracker) and extends them with:

- Deterministic bootstrap via explicit `--initial-members`.
- Joint consensus, learner state, and membership-generation fencing for safe membership changes.
- SWIM + phi-accrual hybrid for accurate failure detection.
- Watch streams for efficient membership distribution.
- Disconnected mode for data-plane resilience.
- Apply-layer determinism guarantees.
- Comprehensive operational primitives and observability.

The non-negotiables for correctness (Phase 1) are joint consensus, learner state, and fencing. Without these, the cluster admits failure modes that violate consensus safety. Phase 2 (robustness) and Phase 3 (operations/performance) are required to meet the SOTA bar but can be staged.

The module lives at `hyperscale/distributed/cluster/`, extends existing `raft/`, `swim/`, `discovery/`, and `server/protocol/`, and introduces no external dependencies beyond OS-level name resolution.
