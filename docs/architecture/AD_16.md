# AD-16: Datacenter Health Classification

**Decision**: Classify datacenter health into four routing states (HEALTHY, BUSY, DEGRADED, UNHEALTHY), plus INITIALIZING for a datacenter no manager has reported from yet, to enable intelligent routing.

**Rationale**:
- BUSY ≠ UNHEALTHY (critical distinction)
- BUSY = transient, will clear when workflows complete (or a worker registers); a job is accepted and queued
- DEGRADED = structural problem, reduced capacity but operational
- UNHEALTHY = severe problem, requires intervention
- INITIALIZING = warmup, not outage; submissions are refused as transient so clients retry
- Routing should actively seek healthier DCs before accepting degraded states

**States** (evaluated in order, `DatacenterHealthManager.get_datacenter_health`,
`datacenters/datacenter_health_manager.py:174-282`):

| State | Condition |
|-------|-----------|
| UNHEALTHY | No managers expected (`total_count == 0`) |
| INITIALIZING | Managers configured but none has ever sent a heartbeat |
| UNHEALTHY | No live heartbeat now (heartbeats existed and went stale), or the authoritative manager reports `storage_writable == False` |
| BUSY | Live managers and `worker_count == 0` (the manager parks jobs until a worker registers) |
| worst of four signals | Otherwise `DatacenterOverloadClassifier.classify` (`datacenters/datacenter_overload_classifier.py:25-56`) takes the most severe of: worker overload ratio, manager unhealthy ratio, manager overload ratio (DEGRADED if the leader is overloaded), and capacity utilization, each against BUSY/DEGRADED/UNHEALTHY thresholds from `DatacenterOverloadConfig`; HEALTHY if none is crossed |

*History (2026-10):* the original table classified `worker_count == 0` as UNHEALTHY and used fixed majority
quorums. That made worker warmup, and total worker loss behind a live manager, terminal: gates accepted jobs
on one view and failed them on another. Zero workers is BUSY and pre-first-heartbeat is INITIALIZING by
design; the code is the better behavior.

**Key Metrics from ManagerHeartbeat**:
- `worker_count`: Total registered workers
- `healthy_worker_count`: Workers responding to SWIM probes
- `available_cores`: Available cores from healthy workers only
- `total_cores`: Total cores across all registered workers
- `overloaded_worker_count` / `stressed_worker_count` / `busy_worker_count`: worker overload signals
- `storage_writable`: the manager's durable-write probe
