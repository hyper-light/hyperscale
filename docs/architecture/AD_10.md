# AD-10: Per-Job Fencing Tokens

**Decision**: Each job has its own fencing-token counter; a dispatch token is `(leader_term << 32) | per_job_counter`.

*History:* this AD first said the token *is* the election term. That was changed to per-job counters (REMAINING_WORK_PLAN D15, 2026-10-05): a term is shared by every job led in it, so on its own it cannot fence one job's dispatches from another attempt of the same job.

**Rationale**:
- Monotonically increasing per job; a token from term N+1 is above every token from term N
- Each dispatch of a job (including retries) gets a distinct, larger token
- Workers can reject stale leader operations and superseded dispatches

**Implementation**:
- `JobManager.get_next_fence_token(job_id, leader_term)` (`jobs/job_manager.py:328`) increments the job's
  counter (low 32 bits) and stamps the term (high 32 bits); called per dispatch at `jobs/workflow_dispatcher.py:970`.
- Included in `WorkflowDispatch`; the worker accepts it only if it is strictly greater than the last token it
  holds for that workflow (`WorkerState.update_workflow_fence_token`, `nodes/worker/state.py:288-302`,
  called from `nodes/worker/handlers/tcp_dispatch.py:143`).
- The SWIM leader's own term-based `get_fencing_token()` / `is_fencing_token_valid()`
  (`swim/leadership/leader_state.py:385-401`) still exist for leader-level operations; they are not the
  dispatch token.
